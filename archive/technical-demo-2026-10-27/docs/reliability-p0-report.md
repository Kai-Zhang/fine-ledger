## P0 场景结果

| 场景 | 操作和断点 | 验收结果 |
| --- | --- | --- |
| 并发打开与跨页面连接 | 12 次并发 open 共用同一 handle；独立模块持有另一实际连接，并另以两个真实标签页复验 | versionchange 关闭各自绑定的 handle，清空后完整恢复 |
| 真实数据库占用 | 额外连接故意不响应 versionchange；收到 blocked 后才释放 | 删除请求继续等待，释放后成功，不提前拒绝或重建数据库 |
| 本机清空后恢复 | 真实 `indexedDB.deleteDatabase`；重新联网初始化 | 业务所有集合及嵌套字段与清空前外部基准完全一致，队列为零 |
| 保存提交前中断 | 在 readwrite 事务 put 后、提交前抛出故障并 abort | 账目、outbox、历史均回滚；关闭数据库重开仍等于原记录 |
| 保存提交后中断 | 本机事务完成后、返回成功前注入异常 | 重开后账目与待上传操作同时存在 |
| 保存后的计时失败 | 第二次计时事务故障 | 主业务提交仍成功，未误报为保存失败 |
| 服务端已提交但本机未应用回执 | 回执返回后、本机应用前异常 | 队列保留；重试后只一笔，队列归零 |
| 回执事务中断 | 本机合并远端 / 游标推进 / 出队事务 abort | 三者全部回滚，不出现“队列清了但账目没拉到” |
| 出队后中断 | 本机应用回执事务完成后异常 | 重开无残留队列，重试游标不增加 |
| NAS 处理前被杀 | `SIGKILL` 于 SQLite 事务之前 | 重启后客户端重发，原操作只接收一次 |
| 日志已持久化、SQLite 尚未提交被杀 | 日志文件及目录 fsync 后 `SIGKILL` | 启动先重放，再接收重试；账目及操作回执各一份 |
| SQLite 提交后被杀 / 丢响应 | 提交后 `SIGKILL`；或主动断开响应连接 | 重试不新增交易或游标变化 |
| 日志写入失败 | 注入 ENOSPC 类失败 | 不返回成功回执，整批 SQL 回滚，原数据及日志批次不变；可重试 |
| SQLite 只读 | 实际开启 SQLite `query_only` 再同步 | 数据库拒写，未返回成功回执，无业务变化 |
| 幂等 ID 内容不一致 | 同一 operation ID 更换票据备注重发 | 拒绝请求，原内容保留 |
| 旧快照 + 增量日志 | 在批次 1 拍快照，继续至批次 4；恢复到不存在的新 DB | 与预先构造的完整期望状态逐字段一致；4 个操作回执保留；重发原操作不重复；`integrity_check=ok` |
| 现有 DB 丢失 / 回退 | 保留独立恢复目录，删除 SQLite；另将现有 DB 回退到旧检查点 | 服务启动自动重放到完整日志末尾，再提供 API |
| 日志损坏 / 缺段 | 修改载荷、移除中间批次 | 校验失败，拒绝恢复，不用部分数据继续运行 |
| 恢复链不匹配 | 不同账本快照、客户端较新游标、错误日志头哈希 | 拒绝混用或同步，客户端记录和队列不被清空 |
| 已有账本恢复目录丢失 | 移除归档再启动 | 拒绝静默重建恢复链 |
| 旧本机 JSON 备份 | 缺少新账目 / 与已有账目内容不一致 | 不删除新记录；差异拒绝覆盖；已有对账不发生未记入 outbox 的变化 |
| 唯一本机副本清空反例 | 保存但不发同步；确认服务端没有该 ID；清空 IndexedDB | 样例确实不可恢复。此为已确认的保护缺口边界，不计作零丢失验收通过 |

桌面客户端中断使用测试钩子触发真实 IndexedDB 事务 abort / 提交后异常并关闭重开数据库，未杀整个浏览器进程。服务端进程中断使用真实 SIGKILL。ENOSPC 是故障注入，SQLite 只读是数据库真实拒写；两者均不能证明物理断电或磁盘固件持久化行为。

## 已补齐的能力和修复

1. 在 SQLite 外部建立带 SHA-256 链的完整增量恢复日志；明确 `synchronous=FULL`。回执前持久化恢复决定，启动时校验并重放，出现不确定写入停止服务。
2. 提供一致性应用快照生成、旧快照加日志恢复 CLI；恢复完整业务、原操作 ID、回执、游标和服务端修订，拒绝覆盖现有目标文件。
3. 幂等校验由“ID 相同即确认”改为“ID 和规范化完整载荷均相同才确认”。每个聚合增加 SAVEPOINT，写入过程失败时不会留下半个聚合。
4. 客户端同步带账本身份、日志批次和日志头；检测游标回退或恢复链分叉，保留本机账目与队列等待处理。
5. 本机事务申请 strict durability。计时、最近账户偏好、新草稿等辅助写入失败不再推翻已提交业务保存的结果；辅助数据失败仍给出具体提示。
6. 收紧旧 JSON 备份为“仅补入缺失记录”。已有差异拒绝覆盖，缺少新 ID 不自动删除新记录；补入影响已完成对账时要求先显式重开。修复原恢复路径可能未写 outbox 就修改既有对账的风险。
7. 完整本机导出补入未提交草稿载荷；它保存在导出文件中，不代表草稿已有 NAS 副本或自动恢复能力。
8. 修复 IndexedDB 首次并发打开可能泄漏连接，以及 versionchange 回调引用可变全局连接的问题。`blocked` 改为等待占用者释放，避免删除请求仍在排队却误报失败后重新建库；实验室运行期间锁住其他动作，并增加明确的清空恢复时间记录。
9. 增加独立实验室、完整外部校验基准、报告导出，以及本机待同步数量 / 最早未保护时间、NAS 日志批次和跨机器备份未配置的状态说明。

代码检查确认两个连接管理缺陷：初次并发打开未复用进行中的 Promise，可能留下多个 handle；versionchange 回调引用可变全局变量，可能关错 handle。另外 blocked 事件即拒绝 Promise 会造成删除请求仍在等待、调用方却认为已结束的竞态。原始 iPhone 阻塞是否同时涉及 Safari 后台挂起没有单独诊断证据；不把上述缺陷当作已确定的唯一根因。修复后用真实并发和真实 blocked 事件复验。第一版协同测试使用隐藏 iframe，在桌面通过但 iPhone 未在时限内响应，尚未执行到删除；原始失败见 [p0-iphone-peer-timeout.json](test-evidence/p0-iphone-peer-timeout.json)。为避免测试基础设施依赖隐藏页面调度，改为独立模块创建实际第二连接，并另以两个真实桌面标签页复验：一页运行 14/14，另一页随后重新连接并匹配完整字段，见 [p0-cross-tab.json](test-evidence/p0-cross-tab.json)。最终手机版本不使用 iframe；iPhone 在 19:25:37 完成全部 14 项并上报，服务端已核实通过。

# MoneyWiz 备份聚合审计（2026-10-28）

本审计只核对时间精度、排序依据、退款关联及原币字段的结构和汇总，不读取消费描述、备注或账户名称，不输出实际交易行、金额、身份标识或配置值。

## 结论

- 历史记录并没有大量落在整分钟：16,824 条物理交易中，显示秒为 `00` 的有 288 条（1.7118%），严格整分钟的只有 160 条（0.9510%）。二者不能混用：前者可以带小数秒。
- 同一账户同一分钟有多条记录的分钟共 180 个，涉及 372 条交易；这些分钟中的记录全部能用现有的整数秒区分，没有同账户同秒或完整时间戳相同的交易。若把历史秒统一改成 `00`，会丢失现有的时间排序信息。数据不能证明 MoneyWiz 编辑时间时具体如何处理秒。
- 退款关联可从备份直接恢复：630 条退款，通过专门关联表完整关联到 578 条原支出。其中 42 条支出有多笔退款，359 条退款入账账户与原支出账户不同。不能把“导入历史退款”设计成必须回原账户。
- 支出上的 `ORIGINAL` 字段虽然有值，但 14,403 条支出的原币和原金额均与账户币种、账户交易金额相同，不能将这些字段视作已保存商户外币数据的证据。
- 没有找到已填充的交易排序序号。保存秒、列表显示到分钟有数据依据；完整时间戳相同时的业务先后顺序，本备份不能证明。稳定 ID 可以用于确定性展示，但不能冒称历史实际次序。

## 方法与来源保护

源为用户指定的 `../iMoneyWiz-Data-Backup`。脚本在 `/private/tmp` 创建独立副本，原样复制 SQLite、WAL、SHM 三个文件，只对副本建立 `mode=ro` 连接并启用 `query_only`。源文件在复制前、复制后、审计后的 SHA-256 完全一致；副本 `quick_check` 为 `ok`。哈希与汇总位于 [aggregate-report.json](aggregate-report.json)，可复现脚本为 [audit.py](audit.py)。库副本不进入仓库，脚本结束自动清理临时副本。

```sh
python3 docs/evidence/2026-10-28-moneywiz-audit/audit.py \
  --source /Users/kai/Documents/projects/iMoneyWiz-Data-Backup
```

这是已冻结文件副本的一致性检查，不是对正在写入的数据库执行在线备份。若源在复制或审计期间变化，脚本停止并拒绝生成“源未变”的结论。

## 数据范围与口径

Core Data 的继承实体共用 `ZSYNCOBJECT`；实体定义来自 `Z_PRIMARYKEY`。交易父实体为 `Transaction`，有实际数据的后代如下。

| WithdrawTransaction | 14,403 |
| RefundTransaction | 630 |
| DepositTransaction | 592 |
| TransferWithdrawTransaction | 590 |
| TransferDepositTransaction | 590 |
| ReconcileTransaction | 19 |
| 合计 | 16,824 |

交易涉及 19 个账户，账户引用全部有效，账户所属用户域为 1 个。实际账户引用字段为 `ZACCOUNT3`；`Z9_ACCOUNT3` 的值对应目标账户实体类型，而不是第二个账户 ID。

所有交易的 `ZSTATUS1=2`、`ZFLAGS1=0`、`ZVOIDCHEQUE=0`。定时交易处理器实体 37–40 为 0 行，其他无数据的交易后代也没有纳入数量。未找到能明确解码的删除或模板状态，也未独立证实状态枚举 `2` 的产品语义，因此本报告不把它擅自解释成“已入账”或“未删除”，也不声称存在可单独排除的删除行口径。

## 时间精度

发生时间字段为 `ZSYNCOBJECT.ZDATE1`，16,824 条都有值。其编码为从 `2001-01-01 00:00:00 UTC` 起的秒数，部分含小数秒；这与 Core Data 结构、按 Apple epoch 得出的 2017–2026 年范围一致。若按 Unix epoch 解释则落在 1986–1995 年。[Apple 官方日期参考说明](https://developer.apple.com/documentation/foundation/date/timeintervalsincereferencedate-swift.property)定义了该参考时刻。

`ZDATE`、`ZCREATIONDATE`、`ZCREATIONDATE1` 在交易行均为空；`ZOBJECTCREATIONDATE` 全部有值，但属于创建元数据，并非另一个已证实的发生/记账日期。没有找到另一个独立银行入账时间字段的有效证据。

计算先使用 `Decimal(str(raw))` 保留十进制值，再四舍五入成整数微秒；不对浮点值直接取余，也不先截掉小数秒。量化的理论容差最多为 0.5 微秒，本库观测到的最大量化误差为 0，按原十进制值和规范微秒计算严格整分钟的结果完全一致。

- “显示秒为 `00`”：整数微秒先向下取整为秒，然后计算秒在分钟中的位置为 0；包括 `00.xxxxxx`。
- “严格整分钟”：规范微秒数能被 60,000,000 整除，要求秒和小数秒均为零。
- “整数秒”：规范微秒数能被 1,000,000 整除，不要求秒数为零。

全年分桶采用 `Asia/Shanghai`。观测年份均为 UTC+08:00，因此与 UTC 相比会影响自然日/年界归属，但不会改变秒数分布或同账户同一分钟的聚类数量。

`ZWITHDRAWREFUNDTRANSACTIONLINK` 明确包含 `ZREFUNDTRANSACTION` 和 `ZWITHDRAWTRANSACTION`，可直接连接退款实体与支出实体，无需通过描述相似度或金额猜测。这是 Core Data 逻辑引用，SQLite 中没有声明受引擎强制约束的外键。

按“每笔原支出的退款数”分布为：1 次有 536 笔支出，2 次有 37 笔，3 次有 3 笔，4 次有 1 笔，7 次有 1 笔。因此旧文档的“630 条退款关联 578 条支出”本次得到独立验证。

该表没有原支出拆分项分摊或历史人民币成本关联字段，不能把交易级关联延伸解释为这些更细的关系。备份保留关系也不代表新产品删除原记录时必须强制连带删除退款；提示用户如何处理关联即可。

## 原币字段与排序依据

全部 14,403 条支出的 `ZORIGINALCURRENCY` 均与所属账户币种相同，`ZORIGINALAMOUNT` 均与 `ZAMOUNT1` 相同。630 条退款、592 条收入也都如此。所有交易类型均未发现原币种与账户币种不同的非空值。少数转入和余额调整的原金额不同或原币字段缺失，详见 JSON，不能单凭字段名字给它们赋予“商户原币金额”语义。

因此历史导入不应要求这批数据不存在的商户原币信息；字段是否允许为空仍属于新产品模型决策，不能从旧库“原币字段均有值”推导出它是用户强制填写的信息。

19 个账户的历史排序设置均为 `date`，`ascending=0`。交易中的 `ZORDER`、`ZPOSITION`、`ZDISPLAYORDER` 及其 1–4 变体均未填值。`ZGID` 全部唯一，`Z_PK` 是行标识；这两者能提供稳定身份，无法证明同秒内的业务顺序。

`ZOBJECTCREATIONDATE` 有 16,810 个不同值，包含 15 个参考 epoch 以前的哨兵值。创建时间也可能是导入/补录时间，不能取代发生时间。本备份没有同账户同秒记录，因而不能实证 MoneyWiz 同秒时采用什么次序。新设计若需要稳定的同秒展示，应明确保存自己的次序或把导入序号用作纯展示兜底，不把它伪装成已经确认的历史先后。

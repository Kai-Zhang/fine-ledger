# 厘序产品反馈整理与设计决定（2026-10-28）

状态：依据本轮反馈修订，供产品 review；未修改前端、账本数据、服务端口或访问方式。

主文档：[产品设计 0.3](product-design.md)。配套修订：[需求 0.8](requirements.md)、[技术设计 0.5](technical-design.md)、[实施计划 0.5](implementation-plan.md)。本文件记录决定及其证据，不将文档完成计为实现或真机验收通过。

## 1. 归档账户，保留账本历史

归档是账户状态，不再需要用“废弃账户”分组模拟。日常首页和新交易的账户选择隐藏归档账户；在“设置 → 账户与分组 → 已归档账户”查看，可取消归档。账户页二级菜单提供归档入口。

- 不要求余额为零，不生成清零交易，不删除旧记录，也不因为归档改变历史净值。报表仍可选择归档账户；默认历史净值保留原有账户范围，不因日常隐藏自动缩小范围。
- 不能以归档账户新增收支、转账端、退款到账或余额调整；恢复新增前先取消归档。
- **用户已确认：允许直接修正归档账户的旧记录**，不必先取消归档。已对账记录仍按普通更正规则提示重新核验。
- 原消费在归档账户中，仍可从它发起退款并退到另一个活跃账户；如果退到该归档账户，则先取消归档。
- 保留原分组和排序，取消归档后恢复；组内均已归档时可从日常首页隐藏整组，管理入口仍保留。

交互上的“隐藏”不等于金额上的“排除”。首页只汇总当前展示的活跃账户，净值报表按自己的账户选择统计。

## 2. 分开设计两种多币种场景

| 场景 | 最短录入路径 | 余额和结算 |
| --- | --- | --- |
| 真正以外币记账的账户 | 以账户外币记消费；主币转入/还款时填两端实际金额 | 账户显示外币余额，换汇发生在跨币种转账/还款 |
| 最终以主币入账的银行卡 | 在主币账户填写估计主币金额、描述、类目，标未入账；银行确认后改同一笔金额并标入账 | 只显示主币余额，后续转账/还款也是主币；不创建临时外币欠款 |

商户原币和银行中间金额是可选补充，**对新记录和历史导入都不强制**。入账后保留消费日期和交易身份，修正金额而非新增第二笔消费；保留旧暂估的更正历史。只凭银行主币实扣额即可确定这类消费的主币成本，之后还款不再重算。

截图中的转出金额、汇率、获得金额可作为跨币种表单的信息结构参考。最终以两端真实金额为准，系统据此派生本笔实际汇率。后续用户明确将汇率来源移出 MVP，因此本轮收敛为手填两端金额；参考报价、刷新和历史报价均后置。

只有一张卡确有独立的外币余额时，才建立对应外币账户并可放入同一组。银行产品称为“多币种卡”本身不是拆账户的依据。

## 3. 草稿移出 MVP，必填项保持

**用户已确认：描述和类目仍然必填。** 不能把去掉草稿理解为允许只填金额保存、默认未分类或无描述。

填写必要信息后保存，之后通过编辑补充项目、备注或更正金额。自动表单持久化、重新打开恢复未提交表单、草稿列表不作为 MVP 门槛。建议未保存离开时确认“继续填写 / 放弃本次修改”，具体手势体验留待交互 review。

保存失败保留当前输入；已保存记录、待同步操作和对账工作进度必须持久化。这些与未提交交易草稿不同。现有原型已有的草稿兼容保留，不在本轮删除旧功能或数据。

## 4. 编辑支持秒，平时显示分钟

- 新建默认当前时间，保留秒；编辑器可选年月日时分秒，普通列表只显示到分钟。
- 调整日期、小时或分钟不自动清零秒；明确改秒才替换该部分。导入保留源小数秒，编辑无关字段不截断时间精度。
- 同账户按完整时间排序，避免显示同分钟的记录顺序随机跳动；完全同时间时仍以稳定身份作确定性排序，但不将其解释为历史真实先后。
- 目前没有数据证明需要新增独立的手工排序字段/界面，暂不增加。
- 转账默认两端同一时间；源两端不同时分别保留，低频的发送/接收时间在更多信息中编辑。

### 备份证据与限度

| 聚合指标 | 结果 |
| --- | ---: |
| 物理交易（保留转账双方） | 16,824 条 |
| 显示秒为 00，含 00.x 小数秒 | 288 条，1.7118% |
| 秒与小数秒都为零的严格整分钟 | 160 条，0.9510% |
| 含小数秒 | 8,001 条 |
| 同账户同一分钟有多条记录 | 180 个分钟，372 条记录 |
| 上述重复分钟可按现有整数秒区分 | 全部 180 个 |
| 同账户同秒冲突 | 0 |

这些数据支持保留已有秒，不支持“MoneyWiz 大多补 00 秒”的假设。没有发现已填充的交易顺序字段；也不能由分布反推出 MoneyWiz 修改日期时具体怎样处理秒。

590 对转账中有 2 对两端时间不同，差值约 0.081342 秒和 15 小时，均未跨上海时区自然日。极小差值也可能跨分钟边界，不能一概解释为延迟到账。

## 5. 保留明确退款关联，不强制共同删除

**用户已确认的原则：有设计和数据支持的关联，可以在删除时询问；询问用于提醒，不意味着强制绑定删除。没有关联则独立处理，不强加关系。**

本次备份实际存在专门退款关联表，630 条关联都有效，连接 630 笔退款和 578 笔原支出；其中 42 笔原支出有多次退款，359 笔退款退到其他账户。这支持保留明确关系，也证明退款到账账户不能限定为原账户。

新退款继续从原消费发起，默认带入类目和项目并保留来源关系：

| 操作 | 行为 |
| --- | --- |
| 删除有明确关联的原消费 | 提示关联退款数，提供“仅删除本笔 / 一并删除关联退款 / 取消”；不默认连带删除 |
| 删除退款 | 默认只删除退款本身，可提示其来源 |
| 没有可验证关联的历史记录 | 独立删除，不猜配对，也不虚构删除提示 |
| 可选回收站恢复 | 各自独立恢复；原消费未恢复时保留“原消费已删除”的历史关联，不自动恢复另一端 |
| 删除/恢复后金额或成本关系有疑点 | 保留事实并列为待核对，不静默改金额，也不用可退额规则阻止恢复历史事实 |

用户可见的撤销与回收站不作为 MVP 必需；内部删除标记、修订和同步保护仍必需。新建关联退款仍检查可退额，与恢复旧记录分别处理。

审计证明的是**交易级关系**，没有证明原拆分项或主币历史成本的细分分配。导入可保留已验证的交易关联，不能凭它伪造细分成本。其他来源缺少关系时保留独立退款，缺失成本按待处理展示。

## 6. 设置中管理分类及图标

“设置 → 收支分类”支持新增、更名、排序、父级调整、归档和图标选择。父类、子类各自拥有图标，优先提供有区分度的图形；暂不以全局唯一图标阻止保存，以免类目数量超过可选图标。

录入继续采用二级展开，避免平铺。更名、图标替换不改变历史金额与身份；移动父级会改变按当前分类树汇总的报表，应预览影响。使用过的类目归档而非连带删除历史交易，已有记录仍可查看其类目。

## 7. 证据范围与后续评审

审计由用户授权的子代理在 SQLite/WAL/SHM 临时副本上完成，只核对结构、关系、时间与汇总，不读取消费描述、备注或账户名，不修改原始备份。源文件审计前后 SHA-256 一致，副本 `quick_check=ok`，临时副本已清理。见 [完整聚合审计](evidence/2026-10-28-moneywiz-audit/README.md)、[汇总 JSON](evidence/2026-10-28-moneywiz-audit/aggregate-report.json) 和 [复现脚本](evidence/2026-10-28-moneywiz-audit/audit.py)。

14,403 条支出的 `ORIGINAL` 金额/币种均与账户金额/币种相同，不能当作已保存商户外币的证据。迁移不要求这批数据没有保存的原币信息。状态枚举尚未独立解码，16,824 是物理记录数，不能直接称为全部有效或已入账交易。此次检查不等于全量迁移金额、拆分或对账验收。

本轮三项澄清已得到回答。随后用户确认：同源自托管、访问密码登录并记住设备；首笔金额记录后锁定主币；汇率来源移出 MVP，跨币种转账手填两端金额。剩余报表口径见产品设计第 15 节，报价供应商不再属于 MVP 待确认项。

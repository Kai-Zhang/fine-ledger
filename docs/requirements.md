# 厘序首版需求与数据模型

版本：0.6
日期：2026-10-28
用途：确定个人记账应用的首版范围、业务规则、逻辑数据模型与验收条件。2026-10-27 开始 P0 产品原型；未执行正式数据迁移。

厘序取精细、准确的账本之意，强调长期积累和有序记录。产品界面和对外文档使用“厘序”；项目 codename 为 `fine-ledger`，用于仓库、包名、服务名和代码引用。

厘序以 iPhone 本地快速记账为核心，启用同步后在服务可达时与所配置的同步服务自动同步，其他 iOS 设备及 Mac、Windows 通过同一套 PWA 查询、记账、对账和查看报表。首版必须承接现有 MoneyWiz 账本中的多账户、多币种、拆分交易、关联退款和对账记录。预算不提供操作界面，但历史数据完整保留。

配套文档：[产品设计](product-design.md)、[技术设计](technical-design.md)、[分阶段实施计划](implementation-plan.md)。产品设计描述用户任务、页面与操作流程，需求描述业务行为与约束，技术设计描述实现边界，实施计划描述交付顺序与验收门槛。

## 产品目标与已确定边界

| 项目 | 要求 |
| --- | --- |
| 使用者 | 单人、多设备；首版不提供家庭成员协作或共享账本 |
| 高频场景 | iPhone 每天新增约 3～10 笔交易，打开、记录、保存、退出 |
| 低频场景 | 每月到每三个月对账；约每三个月或更低频率查看报表 |
| 客户端 | 可添加至主屏幕的 PWA；手机单手操作，桌面适配大屏和键盘 |
| 本地运行 | 完成首次初始化后，离线可新增、修改、查询和查看已有数据报表 |
| 服务端 | 用户选择的同步服务，首版以家庭 NAS 等自托管部署为实施起点；保存已同步数据和历史修订，支持独立备份 |
| 同步条件 | 启用同步后，打开应用、恢复前台及保存后自动尝试；服务不可达不阻塞本地使用 |
| 外出行为 | 同步服务不可达时保留本机数据和同步队列，不影响记账 |
| 主币种 | 建账时可配置，默认 CNY；账户保留独立原币，报表向账本主币种折算。已有记录后的变更流程见产品设计草案 |
| 预算 | 不在首版功能范围；配置、历史关联和原始内容保留 |
| 后台能力 | 不做后台推送、定时唤醒、位置触发和后台同步承诺 |
| 信用卡分期 | 分期计划、分期手续费分摊与分期专用对账不在首版范围 |

下文 NAS 作为当前自托管部署的具体场景，面向用户的入口与状态统一使用“同步服务”；通用配置与连接流程见产品设计。

“已保存到本机”“已同步到服务”“银行已入账”“已对账”“人民币成本已确定”分别表达不同事实，界面与数据模型不得混用。人民币信用卡消费可以已经确定成本但尚未还款；外币信用卡消费可以已经入账但尚未确定人民币成本。

## 首版功能范围

### 账户与余额

- 支持现金、银行和信用卡账户，以及账户分组、排序、归档和是否计入净资产的设置。
- 每个账户只有一种记账币种。已有交易的账户不能直接切换币种；多币种信用卡按币种建立子账户，并可归入同一账户组。
- 支持账户期初余额、信用卡额度和账户余额查询。未用过的透支计息、银行自动计息等能力不做。
- 已入账余额由期初记录和已入账账户流水计算，待入账记录单列。可另外显示含待入账暂估的预计余额，但不能将其用于正式余额对账。余额差异必须通过明确的调整交易修正，不直接修改一个累计余额字段。
- 信用卡欠款以负余额表示，额度作为独立属性；溢缴款允许形成正余额。
- 归档后保留全部历史数据与报表关联，默认不再出现在新增记账的常用账户列表。

### 交易录入与管理

- 支持支出、收入、转账、退款、余额调整五种业务类型。
- 支持日期、账户、金额、币种、描述、备注、分类及旅游项目；日期默认当天，账户可沿用最近选择。
- 支持最近描述、常用分类和账户选择，草稿恢复、连续记账与保存后撤销。
- 支持信用卡待入账记录，保存商户原币金额、银行显示的中间折算金额和暂估 CNY 成本，最终金额未知也能立即保存。
- 银行正式入账后，在原交易上确认账户记账金额与入账日期，保留原币和中间折算历史，不再新增一笔消费。首版由用户补录确认，不自动抓取银行数据。
- 支持按日期、账户、分类、项目、描述、备注、入账状态、对账状态、成本状态组合筛选及搜索。
- 支持交易编辑、逻辑删除和恢复；保留修订历史。引用中的账户、分类、项目采用归档，不能删除后破坏历史关联。
- 保存成功必须以本地数据库事务提交为依据。网络错误、NAS 不可达或远端登录过期不得让已初始化账本无法本地记账。
- 首版不提供独立收付款方档案，名称可写入描述并由历史输入补全。

### 分类与拆分

- 支持收入分类、支出分类和至少两级分类结构，分类层级不可形成循环。
- 一笔收入或支出可以拆为多个分类项，每项记录金额、分类和可选旅游项目。
- 拆分项的币种与交易主体一致，金额合计等于交易本金；不得以浮点误差为理由接受不平衡拆分。
- 分类更名不改变历史身份。首版报表按当前分类树汇总；重分类是明确的数据修改，保留修订记录。
- 转账本金和余额调整不混入日常分类收支。

### 转账与信用卡普通还款

- 同币种转账记录转出、转入账户和等额本金；跨币种转账分别记录两端实际金额与币种。
- 一次转账的两端属于同一业务记录，保存、编辑、同步和删除均保持原子性。
- 普通信用卡还款作为转账处理，不再次形成消费支出；支持全额和部分还款。
- 转入信用卡账户的普通转账默认识别为还款，保留转账用途字段；退款和余额调整使用各自业务类型，不推进还款区间边界。
- 跨币种还款保存实际人民币本金、外币还款本金和结算日期，作为消费人民币成本的来源。
- 银行同一步完成购汇和还款时，记账只需一笔“CNY 账户 → 外币信用卡账户”跨币种转账，不要求创建虚构的外币现金账户或额外换汇交易。
- 先换汇再还款时，按实际资金路径记换汇转账与还款转账，第二步沿用第一步的 CNY 成本来源；用户仍使用转账界面，不重复录入同一笔人民币支出。
- 已知的独立手续费单独记录为费用，并关联转账或还款。汇价中已包含且无法分离的价差体现在实际成本中，不再额外记一遍费用。
- 银行合并扣款可以对应“转账本金 + 手续费”多条关联记录，对账时按合计核对。

### 关联退款

- 退款必须可以关联原支出以及原支出的拆分项，支持部分退款、多次退款和一次退款覆盖多个原支出拆分项。
- 退款总量不得超过可退金额；超额补偿应另记明确的收入或调整。
- 退款账户可以与原支付账户不同；跨币种退款需保留到账币种及实际金额，不得只存一个折算后的数值。
- 退款继承原支出的分类与项目，必要时允许明确分配，避免旅游报表漏扣退款。
- 退款不归为普通收入。报表分别展示支出、退款和净支出。
- 待入账消费被银行撤销且没有实际入账时，将原待入账记录标为撤销，移除其暂估支出，保留修订历史，不虚构退款流水。实际消费已入账后退回资金，才按关联退款处理。
- 已结算消费退款时，冲减对应部分的历史 CNY 消费成本；实际退款收回的 CNY 成本与冲减额不同的部分，作为可追溯的汇兑差额单列。尚未确定实际回收成本时标为待核定。
- 尚未结算的信用卡消费发生退款时，优先抵减对应未结算外币本金，避免之后又对已退款部分分摊还款成本。

### 旅游项目

旅游项目用于聚合某次旅行的机票、住宿、餐饮、购物等费用，和“钱花在什么类别”分开表达。首版用项目替代通用标签入口，不引入行程安排、地图或多人分账。

- 项目包含名称、可选起止日期、备注和归档状态，允许在旅行日期之外关联预订和退款。
- 每个分类拆分项可以属于零个或一个项目；一笔交易涉及多个项目时，以拆分项分配金额，不能把整笔金额重复计入多个项目。
- 录入时可选一个项目并应用于全部拆分项，也可逐项调整。
- 项目报表展示 CNY 总支出、退款、净支出、分类分布及明细，并标识已确定和暂估成本。
- 未设置项目的支出正常进入总报表。
- 旧标签先保留名称、身份和关联，迁移时提供“映射到项目、合并到项目、仅保留历史标记”选项。不能把所有旧标签未经确认都解释为旅行。
- 历史多标签若映射到多个项目，必须确认金额分配；未确认时保留原关联并标记待处理，不复制金额。

### 对账

- 支持按账户、币种和截止日建立对账批次，输入外部账单的期末余额，并逐项核对期间流水。
- 对账页面展示起始已确认余额、期间变动、计算期末余额、外部期末余额和差额；支持交易检索与勾选确认。
- 正式余额与明细对账只包含已入账流水，待入账项目在独立列表显示，不参与已入账余额差额，也不能被标为已对账。
- 同一账户流水只归入一个有效对账批次。仅标记已对账的旧记录保留原状态，不凭空生成历史账单或批次。
- 差额为零且没有相关同步冲突后，才能正式完成对账。确需调整时先创建注明原因的调整交易，再核对。
- 离线可以准备对账草稿。正式完成前要求当前设备与 NAS 同步成功，并提示核实其他设备是否仍有未上传记录；NAS 无法证明离线设备没有待同步内容。
- 对已完成批次中的金额、账户、日期、删除状态等余额相关字段做修改，需要显式重新打开相关批次，并使依赖它的后续批次重新核验。
- 修改分类、项目或备注不改变余额对账结果，但会更新相关报表并保留修订记录。
- 新增或确认入账的流水，若银行记账日期落入已完成批次，需触发相关批次重新核验；业务消费日期较早、但银行记账日期在批次之后的流水，不因此改动旧批次余额。远端迟到数据不得静默改变“已完成”的结论。
- 首版支持普通信用卡账单余额与还款流水核对，不提供分期剩余本金、每期手续费和提前还款核对。
- 银行、支付宝、微信账单文件自动导入及自动匹配不属于首版必需项；首版采用人工余额与明细核对。

## 多币种与人民币成本

2026-10-28 产品方向已扩展为账本主币种可配置。以下 CNY 场景保留为主币种为人民币时的业务样例；通用主币种成本、历史汇率和同步配置需要在产品设计评审后补充技术设计，不代表现有实现已完成泛化。

### 各阶段金额分别保存

| 金额 | 用途 | 是否可被后续还款改变 |
| --- | --- | --- |
| 交易原币金额 | 原始交易及分类拆分 | 不可因汇率变化被改写 |
| 银行中间折算金额 | 例如待入账时银行显示的 USD 金额，作为信息和暂估依据 | 可更新但保留历史，不作为人民币账户正式流水 |
| 账户记账金额 | 对账和账户余额；确认前可未知，确认后必须等于账户币种 | 从未知变为正式金额，之后仅由实际入账修正改变 |
| CNY 报表成本 | 消费、分类和项目报表 | 可由暂估值更新为实际结算成本，保留来源与修订 |

一笔外币消费在消费日归入支出报表。之后还款只是确认这笔消费的人民币成本，不新增第二笔消费。成本确定后回填原消费所属期间，历史报表可能发生修订，界面必须显示成本状态与更新时间。

退款默认按退款发生日展示；项目累计净支出同时扣除关联退款。原消费月份不因后续退款而被悄悄删除消费，但可以下钻查看后续退款。

### 已确认的两种主要信用卡流程

下列流程来自用户当前使用方式。直接购汇还款较多，偶尔先换汇；两者在录入上统一采用转账操作，在成本来源上保留真实关系。

**流程一：信用卡最终以 CNY 入账。** 消费后约 3～5 天内，银行先显示商户原币金额及折算的 USD 金额，暂时没有最终 CNY 金额。此时建立待入账消费，账户仍是 CNY 信用卡，不为中间 USD 数值创建另一笔支出或美元债务。若有参考汇率，可按银行显示的 USD 金额估算 CNY，并保存所用汇率与计算路径；也可从商户原币估算，但两条路径不能叠加。

银行入账后，用户在同一笔交易上填写实际 CNY 金额及银行记账日期，系统确定报表成本，并按原币拆分比例分配到分类与项目，分值尾差按确定性规则处理。消费日期保持不变，原币、USD 中间金额和旧暂估值继续可查。后续 CNY 账户向该信用卡还款只改变账户余额，不再改变消费成本。

约 3～5 天是用户观察到的常见等待期，不是自动入账期限。应用可提示待确认，但不能到期自动认定最终金额。

**流程二：信用卡账户本身以外币记账。** 消费确认后，以该信用卡账户币种记录银行入账金额；商户原币与账户币种不同时分别保留。此时外币余额已经确定，CNY 报表成本仍可能是暂估。偿还时记录 CNY 账户扣款本金及外币信用卡入账还款本金，由这一笔跨币种转账生成实际成本来源，分配到其覆盖的消费。

还款覆盖量按信用卡账户币种计算，不按商户原币计算。例如商户消费以 JPY 显示、信用卡实际欠款以 USD 入账，则还款分配覆盖的是 USD 欠款，再将 CNY 成本分配回该消费的 JPY 分类拆分。

两种流程都允许直接补录已经入账的交易，不要求先创建待入账状态。银行是否入账、外币消费是否已有实际 CNY 成本、是否已对账分别管理。

### 实际成本计算

- 已确认的 CNY 交易本金直接形成确定的 CNY 成本；待入账阶段的 CNY 估算金额不适用这条规则。
- 外币商户消费若由银行直接折为 CNY 入账，以实际 CNY 入账本金确定成本，保留商户原币金额；之后偿还该 CNY 信用卡账单不再次换算消费。
- 外币信用卡消费优先按实际还款对应的 CNY 本金分配成本，而不是把记账当天市场汇率当作最终成本。
- 一次还款可结算多笔消费，一笔消费也可被多次还款覆盖，形成多对多分摊关系。
- 已确认还款分摊不得因后来插入一笔更早交易就被自动重排；需要重新分摊时应明确确认并保留历史。
- 用户录入一次还款的实际两端本金即可，不要求逐笔输入汇率或逐笔确认分配。系统按默认区间生成并保存分配结果；手动调整为低优先级功能。
- 不足以确定实际成本的部分保持“暂估”或“未定价”，不能按零元计入总额，也不能伪装为实际成本。

| 实际路径 | CNY 成本确定时点 |
| --- | --- |
| 外币消费，银行折为 CNY 入账 | 确认银行实际入账金额时 |
| 外币消费，直接用 CNY 还外币信用卡 | 还款实际完成并分配到消费时 |
| 先换汇，再由外币账户消费或还款 | 已知换汇成本，且其来源被分配到消费时 |

“银行直接折为 CNY 入账”与“CNY 购汇偿还外币欠款”不能合并为一种流程，前者不需要等待后续还款才能确定消费成本。

### 默认还款分配规则

默认以相邻两次还款之间入账的交易为分配对象。这里将“到上一次还款期间”具体解释为“上次还款之后、截至本次还款”，不采用银行账单日作为默认边界；这个边界解释在技术设计和验收样例中保持一致。手动调整保留为低优先级，不要求用户每次还款都手选交易。

1. 每个外币信用卡账户独立确定还款区间：以上一笔有效已入账还款日期为起点，本次有效已入账还款日期为终点，默认取 `(上次还款日, 本次还款日]` 内已入账的消费。消费日期不替代银行入账日期；退款、撤销、转账本金不作为新消费。
2. 区间内按入账日期、可用入账时间、稳定流水 ID 排序。为处理部分还款，先覆盖更早期间结转的未偿本金，再处理本期交易；不足部分继续结转，超额部分作为未分配还款或溢缴款保留。这里的先旧后新是边界情况的实现规则，不能遗漏上期剩余本金。
3. 首次还款使用迁移或开户时确认的起始边界及期初欠款项；未知历史欠款不得自动全部归给新消费。只有日期的同日多次还款按稳定还款顺序处理，已覆盖量不得再次覆盖，后来补录的同日交易作为待补分配项处理。
4. 保存默认分配时冻结区间、候选交易、已覆盖本金和规则版本。后续补记或修改旧还款会提示受影响批次，不静默重排已确认成本；手动调整可在低优先级阶段实现，早期版本必须能保留待处理状态和未分配金额。
5. 同一笔还款覆盖的外币本金按实际 CNY 本金比例分摊。例如偿还 100 USD 实际支付 720 CNY，分配给 40 USD 和 60 USD 两笔消费，成本分别为 288 CNY 和 432 CNY；还款自身不计支出。
6. 分次还款分别保留成本。例如一笔 100 USD 消费，先以 288 CNY 结算 40 USD，再以 444 CNY 结算 60 USD，最终成本为 732 CNY。
7. 预先换汇、外币现金及外币资金还款，需要明确资金的历史 CNY 成本。首版允许手动登记已知成本批次、选择来源并分配；不默认开发自动跨账户资金追踪或复杂库存计价引擎。未知成本的还款仍可确认已偿外币本金，成本继续待核定，不能在下次还款中重复覆盖该本金。
8. 外币账户间转账必须能保留已有成本来源引用，不能每转一次就制造新的换汇成本。缺失来源时标为待核定。
9. 早于迁移起点的外币资产或信用卡欠款，作为明确的期初成本／欠款项目处理；对这些项目的还款不能误分摊给新消费。
10. 溢缴款或预付外币保留未分配本金及成本，不强行消耗到当前消费。后续分配必须能追溯来源。

分配按精确比例计算，并按确定性规则处理人民币分的尾差，保证全部分配成本与来源总成本完全一致。来源只覆盖部分本金时，未分配金额继续保留。

### 未结算与历史数据

- 可使用用户维护的参考汇率，或已知最近实际汇率生成暂估；必须保存汇率日期、来源和估值时间。首版不依赖在线汇率服务。
- 已结算部分与未结算部分分别计算。总成本为“已确定成本 + 剩余部分暂估”，不得用新汇率重算已经确认的部分。
- 没有可用参考汇率时显示未定价原币金额。报表显示“合计不完整”，不显示一个看似完整的 CNY 总额。
- MoneyWiz 导入能保留原汇率字段，但仅凭这些字段或还款日期不能证明逐笔成本关系。能验证的实际关系才标为确定，其余为“历史暂估”或“待核定”。
- 不要求用户为了启用新应用而逐笔重建全部历史结算；可以分批确认来源或继续保留明确标注的历史暂估。
- 对账完成不等于人民币成本确定，反之亦然。外币账户余额可以完全正确，但消费的 CNY 成本仍未确定。
- 旧库没有保留商户原币或 USD 中间金额时，不反推或捏造这些字段；已确认的 CNY 账户入账金额可以直接作为历史实际成本，外币账户仍按可验证的成本来源处理。

### 收入与净资产口径

“还款汇率”只直接适用于相应的外币欠款，不能直接用于所有外币收入和存量资产。

- 外币收入首版使用显式确认的 CNY 金额或带来源的参考汇率暂估；首版不实现外币收入后续换汇的全自动回溯分配。
- 账户页始终显示原币余额。CNY 净资产属于余额估值，按报告日期及所选参考汇率转换，并展示估值口径与缺失汇率。
- 净资产估值不改写消费的实际 CNY 成本。历史余额趋势可以按各期可用汇率估值；缺失时标明缺口。
- 汇兑差额、手续费、退款分别展示，不能通过修改原币本金来“对平”报表。

## 报表与交互

### 首版报表

| 报表 | 展示内容 |
| --- | --- |
| 收支趋势 | 月度、季度收入、支出、退款与净支出；转账本金和余额调整排除 |
| 分类收支 | 分类和子分类汇总，可下钻到拆分项与原交易 |
| 旅游项目 | 项目总支出、退款、净支出、分类构成、成本确定程度 |
| 账户余额 | 单账户原币余额及历史变化；分组汇总须明确币种 |
| 净资产 | 资产与信用卡负债的 CNY 估值，显示汇率日期和来源 |
| 待处理 | 待入账交易、未对账交易、同步冲突、未结算／未定价金额、待确认迁移关系 |

全部报表支持日期、账户、分类和项目筛选。CNY 汇总同时给出确定金额、暂估金额和未定价原币余额。离线报表基于本机副本，并展示最近同步时间。

收支与项目报表默认按消费日期包含待入账消费，并明确标为暂估或未定价；用户可筛选仅看已入账交易。账户余额和默认净资产估值只采用已入账流水，若展示含待入账项目的预计值则单独标注。待入账转为正式入账是同一笔交易更新，任何视图都不能双计。

### 手机与桌面

- 手机主要入口为记账、账单、报表和设置；项目从记账及报表进入，避免新增过多导航层级。
- 金额、账户、分类、保存放在常用位置；项目可一键沿用但需要可见，防止旅行结束后误标。
- 备注、拆分、成本分配和调整原因按需展开，简单支出不要求填写全部字段。
- 待入账确认入口集中列出交易日期、商户原币金额、可选 USD 中间金额和描述，允许补填最终账户金额及入账日期；原有分类、拆分、备注和项目自动沿用。
- 跨币种还款仍使用转账表单，输入两端实际金额即可形成成本来源并按默认区间自动分配；存在未知期初项、冲突或缺失成本时保留异常状态，不阻止先保存真实转账。
- 输入草稿在切换应用、锁屏后恢复；保存失败保留输入。后台退出前不能只保存于内存。
- 桌面提供交易列表与明细并排、键盘录入和对账布局；手机也能完成核心功能，不要求依赖电脑才能修正账本。
- 首版性能目标：目标真机上本地保存反馈 P95 不超过 200 ms；初始化后离线冷启动至可记账目标不超过 2 秒。它们是待验证目标，不是当前性能结论。

## P0 快速记账交互约定（2026-10-27 评审输入）

1. 首页以紧凑分组账户列表为入口，首屏优先显示账户余额；分组可折叠并按币种分别合计。点账户进入该账户交易记录，再记一笔；账户行另有快速新增入口。连续保存保持当前账户，正常流程不要求每笔从长列表重新选择。录入页允许主动切换账户。
2. 描述采用应用内可点选的横向候选条；手机输入描述时随可视区域停靠在键盘上方，不占用系统输入法的原生候选栏。空输入展示最近 8 个不同描述；输入后匹配任意 substring，prefix 优先，同一优先级按最近发生时间排序。匹配忽略英文大小写与全半角；输入法组合期间不劫持 Enter。
3. 选择描述后带入该描述同一收支类型最近一次使用的二级类目；用户可覆盖。类目按一级分组展开二级项，不全部平铺。描述补全不偷偷沿用旅游项目。
4. 旅游项目和备注默认折叠，作为可展开的选填信息；恢复的草稿若已有内容则展开显示。
5. 发生时间默认当前时间，可配置至分钟；以带秒的 ISO UTC 时间戳储存，分钟选择对应秒为 00，本地展示日期与时间。消费时间与银行入账日期仍为不同字段。
6. 退款从原支出详情发起，沿用原类目和项目，支持部分、多次退款及剩余可退额校验。普通新增类型不含退款。
7. 余额调整从具体账户的“更多”二级菜单发起，输入实际余额和调整原因；保存独立差额流水，不计日常收入与支出。普通新增类型不含余额调整。
8. 日常页面突出账户、交易和保存结果。去掉隐藏金额按钮、弱信息抬头、常驻教学说明与 P0/原型等阶段标签，review 页面也按正式产品呈现。NAS 连接、本地数据库、缓存版本等技术信息默认不出现，放在设置中可开启的开发者信息内。需要用户处理的保存错误必须直接反馈，不能被开发者开关隐藏。

9. 所有已有记录支持逻辑删除，交易详情内提供入口；删除后可撤销，也可在设置的“最近删除”恢复。删除及恢复同步更新余额、报表和描述历史；有有效关联退款的原消费需先删除退款，恢复退款需重新校验原消费及可退量。历史内容与操作意图必须保留。

以上约定用于 P0 产品体验评审，不表示 P1–P6 的完整账务、同步、迁移与恢复验收完成。P0 先演示原账户同币种退款及同币种转账；完整跨币种退款、拆分退款等业务范围仍按 P3/P4 实施。

## 逻辑数据模型

以下是业务实体及约束，不是最终 SQL。客户端和 NAS 的物理表结构可以不同，但金额、关系与状态必须一致。

### 账本和业务实体

| 实体 | 核心字段 | 关系与约束 |
| --- | --- | --- |
| Ledger | id、名称、base_currency、业务时区、默认汇率策略 | 首版单账本，base_currency 固定 CNY；日期归属使用账本业务规则 |
| Currency | code、minor_unit_digits | 支持 CNY、JPY、USD；JPY 不按两位小数处理 |
| AccountGroup | id、ledger_id、名称、排序、archived_at | 账户分组；历史引用保留 |
| Account | id、group_id、类型、币种、额度、是否计入净资产、排序、archived_at | 单币种；信用卡余额符号规则统一 |
| Category | id、收入或支出类型、parent_id、名称、排序、archived_at | 父子类型一致，无循环；保留稳定身份 |
| Project | id、名称、起止日、备注、archived_at | 可表示旅行；不以日期强制限制交易关联 |
| Transaction | id、类型、转账用途、业务日期、可选发生时间、原币及本金、描述、备注、related_transaction_id、revision、deleted_at | 转账用途区分普通转账、还款和换汇；两端金额以流水为准，交易原币字段可空 |
| AccountPosting | id、transaction_id、account_id、posting_state、记账日期、有符号账户金额 | pending、posted、voided；pending 时日期和正式金额可空，posted 时必填且使用账户币种；只有 posted 参与正式余额和对账 |
| BankAmountObservation | id、transaction_id、posting_id、阶段、币种、金额、观察时间、来源、supersedes_id | 保存银行中间折算金额，例如 USD；可以没有；不能直接参与账户余额或作为额外支出 |
| CategorySplit | id、transaction_id、category_id、project_id、原币金额、备注 | 普通收入／支出拆分合计等于本金；项目可空 |
| RefundAllocation | id、refund_transaction_id、original_split_id、原币退款对应量、到账分配金额 | 关联原支出拆分项；可表达多次退款与跨币种到账 |
| ReconciliationSession | id、account_id、起止日、起始确认余额、外部期末余额、状态、完成时间、revision | draft、completed、reopened；记录前序批次关系 |
| ReconciliationItem | session_id、posting_id、确认时流水 revision | 完成批次保留核对版本；旧数据允许只有历史已对账标记 |

首版余额计算采用账户流水模型，不强行引入完整企业会计科目表。两条不同币种的转账流水不能直接按数值求和为零；必须分别核对两端本金与成本来源。

期初余额是明确的期初流水，调整是明确的调整流水；二者都不进入日常收入支出。交易业务日期、银行记账日期、数据创建时间和最后修改时间分别保存。

待入账交易保留稳定的 Transaction、AccountPosting 和 CategorySplit 身份。确认入账以同一业务修订填写正式金额、更新 posting_state 并建立成本或暂估关系，而不是新增第二笔交易。正式入账后再次更正遵守已对账数据的重新核验规则；撤销未入账记录使用 voided，且不删除其历史。

### 结算与估值实体

| 实体 | 核心字段 | 关系与约束 |
| --- | --- | --- |
| CostSource | id、类型、来源交易或期初项、日期、外币本金、CNY 本金、已分配量、确认状态、依据备注 | 来源可以是 CNY 直接结算、换汇批次、信用卡还款或人工确认的历史成本；费用独立 |
| CostAllocation | id、source_id、目标流水或拆分项、覆盖的账户币种金额、对应原币量、分配 CNY 金额、revision | 来源和目标多对多；同一目标本金不能重复覆盖，来源不能超额分配 |
| CostSourceLink | id、上游来源、下游来源、传递的外币本金与 CNY 成本 | 外币资金转移或用于还款时传递来源，避免复制可用额度；不允许循环 |
| RepaymentBatch | id、还款交易 id、信用卡账户、前次还款 id、区间边界、规则版本、候选快照、状态、revision | 每笔外币信用卡还款对应一个自动分配批次；保存例外及后续调整历史 |
| RepaymentCoverage | id、batch_id、目标流水或期初欠款项、覆盖外币本金、关联成本分配 id | 区分实际已偿本金和 CNY 成本是否已知；不得重复覆盖，费用或退款按明确关联处理 |
| ValuationRate | id、from_currency、to_currency、rate、effective_date、source、用途 | 区分未结算暂估和资产估值；汇率采用精确十进制 |
| CostValuation | target_id、已确认部分、暂估部分、未定价原币量、rate_id、估值时间、输入 revision | 可重新计算的报表结果，不是新的账户流水；历史估值可保留用于解释变化 |
| CurrencyDifference | id、相关退款或结算、CNY 差额、状态、说明 | 表达成本冲减与实际回收之间的汇兑差额；不能伪造账户流水 |

普通信用卡还款以 Transaction 和 AccountPosting 表达真实资金移动，以 CostSource 和 CostAllocation 表达消费成本确认。两种关系相互关联，但分别约束，避免把还款当作第二笔支出。

成本覆盖度由实际成本分配量推导为未覆盖、部分覆盖、完全覆盖；成本质量单独标记为确定、暂估、历史暂估或未定价。这不是信用卡是否已还款的标志，尤其不能将流程一中已经确定 CNY 成本的消费显示成“已还款”。退款会影响可分配的本金，必须在分配校验中考虑。

退款成本冲减记录通过 RefundAllocation 关联原始 CostAllocation，不删除原消费曾经使用的成本来源。已结算后退回的可再次使用外币，建立关联退款的新成本来源；未结算本金被退款抵减则不生成虚构的 CNY 成本。明确区分这两种情况，避免同一历史成本既被释放又被重复新增。

### 迁移和同步实体

| 实体 | 核心字段 | 关系与约束 |
| --- | --- | --- |
| ImportBatch | id、来源、源文件校验值、导入版本、状态、校验摘要 | 同一备份重复导入不重复生成业务记录 |
| LegacyMapping | batch_id、源实体、源主键或 GID、目标实体与 id | 保留转账配对、退款和分类关系的来源 |
| LegacyRecord | batch_id、源实体、源 id、保留内容、处理状态 | 保留预算、旧标签和暂不转换的业务字段；不进入实时收支汇总 |
| Device | id、名称、最近连接时间、last_server_cursor | NAS 只能知道已连接设备的同步进度 |
| ChangeOperation | operation_id、device_id、aggregate_id、base_revision、payload、状态 | 业务修改与本地队列同事务写入；上传可重试且幂等 |
| EntityRevision | entity_id、revision、修改时间、来源设备、变更内容 | 保留历史；删除使用墓碑标记 |
| SyncConflict | id、业务对象、基础版本、本地版本、远端版本、解决状态 | 金额、账户、对账和成本分配冲突不得静默覆盖 |

预算历史至少保留预算对象、账户关联、分类关联、交易关联及期间统计原始字段。原始 SQLite 和 WAL 备份单独归档，不把旧账号密码、登录令牌等认证字段带入新应用业务库。归档按敏感备份保护。

### 金额和一致性约束

- 账户金额使用币种最小单位整数，汇率使用精确十进制；接口不得因 JavaScript 数值范围而丢失整数精度。
- 所有业务对象使用独立稳定 ID，旧库主键只用于迁移映射。
- 业务交易、账户流水、分类拆分以及对应同步操作在一次本地事务中提交。
- 转账两端、退款分配和成本分配作为有约束的业务聚合修改，服务器也需原子校验与提交。
- 删除已被退款、成本分配或已完成对账引用的交易，需要显式处理依赖，不能留下孤立关联。
- 报表只从有效业务数据生成，排除墓碑、迁移暂存记录和失效估值；物化余额与报表缓存可以重建。
- 一个成本来源向下游传递的成本加直接分配的成本不得超过原始成本，防止跨账户或多次还款重复计价。
- 中间折算金额不得写入币种不匹配的正式账户金额字段；pending 时未知金额用空值表达，不能以零表示“尚不知道”。
- 待入账确认、正式流水金额、成本来源及对应分配的变更需要原子提交。跨设备重复确认或同时填入不同正式金额时，按同一交易的版本冲突处理。

## 同步与部署要求

- 前端静态资源与 API 由 NAS 的稳定 HTTPS 来源提供；首次在家完成初始化和离线资源准备，再允许依赖外出离线使用。
- 使用可信证书和稳定域名。域名、协议或端口变化视为来源迁移，不能假设自动访问旧本地数据。
- 应用启动、恢复前台、保存后和前台重试时尝试同步。网络切换不一定产生 online 事件，因此必须以 API 请求结果判断 NAS 可达性。
- 本地操作队列批量上传，服务端按 operation_id 幂等处理；服务器提交成功后才确认，本地收到确认后才移出待同步队列。
- 按服务端游标增量拉取，不依赖客户端时钟排序；拉取不得覆盖本地尚未确认的修改。
- 同一对象使用版本检查；冲突保留双方数据。余额相关、对账和成本来源冲突必须显式解决。
- 长期未连接设备超过增量保留期限后获取新快照，同时保留并重新校验本机待同步操作，不能直接抹掉它们。
- 退出应用时仍未同步的数据只能保证已保存于本机；换机前应在家完成同步并核对待同步数量为零。
- 本地存储不可作为唯一副本。NAS 版本备份与实时同步分开，备份应至少有一份位于不同故障介质；支持完整导出和恢复演练。
- 更新应用和升级本地数据库结构时，保留未同步操作及草稿，失败不得通过清空数据库恢复启动。
- 远端认证过期不阻止已有本地账本记账；重新同步前恢复认证。新设备必须联网认证并初始化。首版信任自有 NAS，不宣称端到端加密。

## 历史数据迁移

迁移来源为本地 MoneyWiz SQLite 备份及其 WAL。转换在副本中执行；原始文件只归档、不修改。下列数量是此前结构检查得到的迁移核对基线，不代表需要复刻 MoneyWiz 的全部界面。

| 项目 | 基线 |
| --- | --- |
| 账户与分组 | 19 个账户、4 个分组，币种 CNY、JPY、USD |
| 交易物理记录 | 16,824 条，转账双方分别存储 |
| 转账 | 590 对，其中 64 对为不同账户币种 |
| 基础交易 | 支出 14,403 条、收入 592 条、退款 630 条、对账调整 19 条 |
| 业务数量参考 | 转账合并后约 16,234 笔，不以简单源行数等于目标行数验收 |
| 分类 | 当前用户配置 48 个，26 个子分类，35 个实际关联交易 |
| 拆分 | 467 笔交易使用多个分类 |
| 退款关系 | 630 条退款关联 578 笔原支出，42 笔原支出有多次退款 |
| 历史已对账标记 | 8,707 条物理交易记录，不等于同数量的业务交易或对账批次 |
| 标签与预算 | 6 个标签关联 155 笔交易；2 个预算保留历史、不提供首版操作界面 |

迁移先预览再确认。需要校验各账户原币余额、各交易类型数量、转账完整性、拆分合计、退款关联、对账状态和历史归档完整性。旧库浮点金额转换的舍入差异必须列出，不能无提示修改余额。

对重复别名列、用户域、父类／子类实体，按源数据关系解析，不能将物理列名相近视为同义。当前用户账本之外的预置或其他用户数据不混入业务账本。

历史预算和旧标签应可随完整导出带走；历史成本缺失不阻塞基础迁移，但其影响必须在报表中可见。迁移完成后，至少用一个历史月份及每个账户的余额人工核验，再接替旧应用。

## 首版验收条件

| 场景 | 通过条件 |
| --- | --- |
| 离线冷启动 | 初始化后断网、关闭再打开，仍能进入记账页并查询已有数据 |
| 本地保存 | 保存成功后强退再打开，交易、拆分和待同步操作完整存在 |
| 回家同步 | 在家打开应用，无需点击同步即可上传待处理操作并拉取修改 |
| 网络中断与重试 | 上传中断、响应丢失、重复发送均不产生重复交易或半笔转账 |
| 多设备冲突 | 同一交易被分别修改时保留双方并要求解决，不静默覆盖金额 |
| 拆分与项目 | 拆分合计正确；项目与分类汇总不因多次关联重复计数 |
| 退款 | 部分退款、多次退款正确减少可退额与净支出，原关联可追溯 |
| 跨币种还款 | 100 USD 以 720 CNY 偿还后，对应消费成本合计 720 CNY，且还款不重复计支出 |
| 银行折成人民币入账 | 原币消费与 CNY 入账金额同时保留，后续 CNY 还款不改变已确定消费成本 |
| 待入账转为人民币入账 | 合成样例：10,000 JPY、银行显示 67 USD、暂估 482.40 CNY，随后实际入账 490 CNY；同一交易成本更新为 490 CNY，原币与 USD 信息保留，消费归属原日期且不双计 |
| 待入账余额 | 上述样例确认前不进入 CNY 账户正式余额；确认后形成一条 -490 CNY 流水，报表暂估被实际成本替换 |
| 待入账撤销与超期 | 撤销后不产生虚构退款；超过常见 3～5 天仍未确认时只提示，不自动入账 |
| 购汇还款一步完成 | 一笔 CNY → 外币信用卡转账即可记录两端资金并提供成本来源，不要求虚构中间账户 |
| 相邻还款区间 | 上次还款 9 月 10 日、本次 10 月 10 日，选择 `(9 月 10 日, 10 月 10 日]` 入账交易；9 月 9 日消费但 9 月 12 日入账的交易进入本期 |
| 结转与未知成本 | 上期剩余本金优先覆盖；已偿但 CNY 成本未知的本金不被下次还款重复分配 |
| 分配边界例外 | 首次、同日多次、超额及补记旧交易均不漏账或静默改写既有成本；未解决项明确可见 |
| 先换汇后还款 | 两笔实际转账传递同一 CNY 成本来源，不能重复生成或重复消耗成本 |
| 部分结算 | 一笔消费跨两次汇率结算时，已确认部分不变；剩余部分明确暂估或未定价 |
| 结算与退款交叉 | 已退款的未结算本金不再分配还款成本；已结算退款正确冲减成本并单列差额 |
| 成本尾差 | 分配后的 CNY 分值合计与来源总额严格一致，可解释尾差归属 |
| 余额估值 | 未定价资产不按零计入完整净资产；估值汇率不改写消费成本 |
| 对账 | 差额非零不能直接完成；修改历史余额相关字段会触发重新核验 |
| 迁移 | 账户余额、类型与关系校验通过；预算历史和旧标签可追溯并可导出 |
| 备份恢复 | 从独立备份恢复到账本副本，余额、交易关系和成本来源保持一致 |
| 升级与长时间离线 | 升级失败、旧设备重新接入不会清空本地待同步记录 |

验收数据应使用合成样例，覆盖 JPY 零小数位、多次退款、分次还款、旧账期初欠款、外币预存资金和已对账后补记等情况。真实备份用于只读迁移核验，不作为可破坏的测试数据。

## 后续功能与待确认事项

信用卡分期作为独立后续阶段：需要分期合同／计划、总本金、期数、每期本金与手续费、实际账单、提前还款和剩余负债。当前版本保留稳定交易、账户流水、对账批次和关联 ID，后续可以引用原消费；本期不预建空的分期业务界面，也不把普通部分还款等同于分期。

还款分配的手动调整是低优先级扩展：数据模型必须支持版本化修正，但不阻塞首版默认自动分配上线；早期异常可保留待处理或未分配，不伪造已确认结果。预算编辑、预算进度、银行账单自动导入、自动匹配、附件、自动周期交易、投资、贷款和后台推送均在首版之外。

| 待确认项 | 本草案处理 |
| --- | --- |
| 外币资产历史 CNY 成本 | 提议支持人工登记成本来源，未知则暂估或未定价；不要求重建全部历史 |
| 旧标签映射 | 迁移预览时选择项目或仅保留历史标记，不在当前阶段分析具体旅行内容 |

本文件已确定产品范围与实体职责；表中尚未确认的计价规则应在实现相关模块前确认，不影响先细化本地记账、NAS 同步、历史保留和普通对账需求。

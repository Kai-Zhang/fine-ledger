**R1 · P1 · 本机事务只检查被改对象，未检查关联数据与合并后的业务约束**

位置：`src/storage/repository.ts:300–333`；`src/components/AccountEditor.tsx:103–112`。

`mutate()` 在 `editBase` 的旧账本上运行业务操作，只比较 delta 内的实体是否变化，然后把结果应用到最新账本并直接写库。其他实体的变化不会触发冲突，合并结果也没有用最新账本作为 previous 再校验。

复现：打开一个尚无交易的 CNY 账户编辑器并准备改为 JPY；另一个页面先新增一笔 `amountMinor=10000` 的 CNY 支出；旧编辑器随后保存。账户对象本身没有变，因此并发检查通过；旧快照中也没有新交易，因此“已有交易不能改币种”检查通过。最终已存在的 100.00 CNY 被解释为 10,000 JPY。本机提交成功，而以保存前最新账本为基线调用 `validateBook` 会拒绝该改动。另一复现是旧交易表单向已经被其他页面归档的类目添加新交易。

影响：即使服务端稍后拒绝同步，本机账本和显示金额已经改变；部分关联变化还可能成为被服务器接受的新状态。

方案：在同一 IndexedDB 事务内，以最新账本复核语义依赖，包括账户币种/归档状态、类目/项目、退款及转账来源；对候选合并结果执行统一业务校验。不能仅增加最终全量校验，因为“旧表单金额被重新解释为新币种”可能在最终结构上合法，还必须检查表单所依赖的版本或明确记录输入币种。短期先封住数据边界，随后用实体索引和受影响范围校验降低开销。

验收：跨页面新增交易与账户改币种竞争、归档与新增交易竞争、删除/修改退款来源竞争均应原子拒绝或要求重新确认，保留用户输入，失败不能写入 book/outbox/revisions。

**R2 · P1 · 初始化后直接采用较新的远端快照作为基线，会把其他设备修改当成需要撤销的差异**

位置：`src/sync/engine.ts:553–575`。

`completeInitialization()` 提交 `init.book` 后重新获取 session 和 snapshot，并把 snapshot 保存为 baseline，却没有把初始化提交后的远端变化合并回本机。若另一设备在初始化已提交、快照尚未读取的窗口修改数据，本机仍是旧值，baseline 却已经是新值。

复现：A 发布空服务；初始化成功后，B 将账本名称修改为新值；A 获取包含 B 改动的快照，继续正常同步。B 的名称被 A 静默改回初始名称，状态显示 idle，未出现冲突。相同机制适用于其他可更新实体；新增/删除涉及关系约束时也可能转为拒绝同步，不能简单概括成所有变化都会丢失。

方案：用初始化回执对应的 cursor 和版本建立准确基线，再走正常增量拉取；或显式以 `init.book`、当前本机账本、最新 snapshot 做三方合并并保留冲突。不能直接用最新 snapshot 的版本认可本机尚未见过的数据。

验收：初始化后至 snapshot 前插入第二设备编辑；覆盖初始化回执丢失重试、本机同时新增编辑、远端同一实体编辑与独立编辑。

**R3 · P1 · PWA 更新把未及时答复当作允许刷新**

位置：`scripts/templates/service-worker.js:36–50`；输入当前主要保存在 `src/pages/EntryForm.tsx` 的 React 状态中。

更新握手等待 400 ms，超时返回 null；激活逻辑只排除明确的 `safe === false`，因此 null 会执行 `client.navigate()`。页面主线程繁忙、后台暂停或消息处理延迟时，“未收到回复”不等于“没有未保存输入”。

复现：VM 中将旧页面的 `{safe:false}` 回复延迟至 600 ms，400 ms 时已调用 navigate。确认的是强制导航路径；真实 iPhone 上输入丢失尚未单独验证。

方案：只有收到明确 `safe === true` 才自动导航；未知/超时保留页面，待前台或用户保存后重试。旧版客户端升级另设明确路径。必要时补充草稿持久化，不能用 beforeunload 代替更新协议保护。

验收：无回复、延迟回复、页面阻塞、后台恢复、编辑中升级均不得自动丢弃输入；空闲页面仍可正常更新。

**R4 · P2 · 新 Service Worker 接管旧页面后，保留的旧缓存无法用于离线资源请求**

位置：`scripts/templates/service-worker.js:45–52,89–98`；`src/reports/useReport.ts:40–43`。

激活时 `clients.claim()` 接管仍在编辑的旧客户端，并刻意保留旧版缓存。但 `resource()` 只查询当前 `CACHE`，没有按 `/assets/<release>/` 查找旧版缓存。旧页面稍后创建旧版报表 Worker 时，离线请求仍会走网络并得到 503。

复现：旧版缓存中放入合法报表 worker，当前 worker 处理该资源请求，禁用网络，返回 503。此复现没有打开真实浏览器。

方案：对带版本的同源静态资产精确查询其对应 release 缓存，限定路径和缓存前缀；让仍被客户端引用的版本继续可用。不要扩大到 API 或任意缓存匹配。随后只清理不再被任何活跃客户端使用的旧版本。

验收：旧编辑页延迟更新后断网，保存并进入报表仍能加载旧资源；无活跃客户端引用的旧版本可以回收。

**R5 · P2 · 有期初余额但没有交易的账户，前端允许改币种，服务端拒绝**

位置：`src/components/AccountEditor.tsx:62–66,103–112,165–172`；`src/sync/protocol.ts:231–235`。

UI 的 `hasHistory` 和提交检查仅考虑 entries，选择币种时还会把期初余额设为 0。服务端则要求旧账户的 `openingMinor === 0` 且没有金额记录。两端使用不同规则。

复现：创建一个有 100.00 CNY 期初余额、无交易的账户并同步；本机改为 USD 并按 UI 逻辑重置余额到 0；本机保存成功，随后同步进入 conflict，原因是“已有金额记录的账户不能修改币种”。

方案：提取共用的 `canChangeAccountCurrency` 规则，在表单、保存事务和协议校验中共用；依现有服务端规则，有非零期初余额也应锁定币种。避免把余额静默清零作为改币种的副作用。

验收：零余额无交易可改，有期初余额或含已删除交易的账户按一致规则拒绝；本机不能先接受服务器注定拒绝的状态。

**R6 · P2 · 报价缓存把请求截止日当成数据已经完整的截止日**

位置：`src/reports/useReferenceRates.ts:22–24,74–80,155–157`。

成功响应即写入 `{through}`，即使响应中尚无当天报价；之后同一天每小时刷新、回到前台、恢复网络都会因 `current.through >= through` 跳过请求。空数组也会被标记为已覆盖；历史年份一旦标为完整也不会再检查数据缺口。

复现：请求至 2026-11-05，mock 只返回 11-04 报价；之后 mock 已有 11-05 报价，再调用同日刷新仍只有一次网络请求，缓存最新日期仍为 11-04。

方案：分开存储 requestedThrough、latestQuoteDate、fetchedAt；近期区间使用有界 TTL，并对最近数个交易日重抓，已关闭历史区间采用更长缓存。周末/节假日不能简单视为错误，也不能以缺当天报价无限重试；保留退避和离线缓存。

验收：当天先无报价、稍后发布；合法休市；空响应；429；离线回读；并发区间刷新均有明确行为。展示实际报价日期以便理解暂估金额。

**R7 · P2 · 单笔保存与同步仍多次扫描、克隆和序列化整本账**

位置：`src/storage/repository.ts:300–333`；`src/sync/model.ts:46–71,178–187`；`src/sync/engine.ts:325–418,450–476`；`server/store.ts:101–118,342,471`；`server/app.ts:190–206`。

客户端 `changesBetween()` 比较所有实体，`applyChanges()` 克隆整本账，保存和应用同步批次都会重复执行。服务端每个 push 重新读取和校验整本账；空 pull 和 session 摘要也读取全账。报表计算已经有 Worker，但这条同步路径仍运行在浏览器主线程，服务端同步 SQLite/JS 工作也占用事件循环。

本机单次合成实验如下，仅用一个账户和普通单拆分交易，不等于真实数据复杂度，也不是统计意义上的 p95 或 iPhone 性能：

| 操作 | 16,000 笔（JSON 4.6 MiB） | 32,000 笔（JSON 9.3 MiB） |
| --- | ---: | ---: |
| 全账业务校验 | 64.9 ms | 111.9 ms |
| 计算单笔变化的 diff | 97.4 ms | 194.4 ms |
| 生成单笔同步命令 | 162.9 ms | 343.5 ms |
| 服务端单笔 push | 87.6 ms | 163.9 ms |
| 服务端读取整本账 | 13.4 ms | 31.2 ms |
| 无变化的 pull | 13.2 ms | 27.8 ms |

方案：先用 SQL 读取摘要/账本 ID，消除空轮询全账装载；复用索引和版本映射，减少同一次操作的重复 clone/diff；将可转移计算移到 Worker，并保证结果落库时重新核对 revision。中期把 IndexedDB 拆成实体表，在业务命令里直接记录增量，对受影响关系做增量校验。不要未经基准测量直接重写整个存储层。

验收：建立 2 万/5 万/10 万笔固定合成数据与含退款/转账的数据集；分别测保存反馈、空轮询、积压同步、服务端事件循环阻塞、真机长任务和内存峰值。性能目标应以目标设备实测设定。

**R8 · P2 · 本机恢复历史与旧壳缓存缺少容量生命周期，完整导出却有硬上限**

位置：`src/storage/repository.ts:332,360–396`；`src/storage/archive.ts:29–32`；`scripts/templates/service-worker.js:52`。

每次 mutate 都新增 revisions；同步 compact 只清空 outbox，不清理 revisions。完整备份导出所有修订与恢复副本，序列化后超过 64 MiB 就拒绝导出。Service Worker 的历史 release 缓存也没有安全清理实现。正常同步成功不会阻止这些数据继续累积。

影响：长期使用后会增加 IndexedDB/缓存占用、完整导出内存和失败风险。确认的是代码中无日常保留/容量管理及硬上限，不是当前生产设备已经达到配额。

方案：给已确认修订建立可配置保留和归档策略；绝不能回收待同步、冲突、恢复所必需的数据。增加存储占用与可导出性检查；提供仅含当前有效账本的可恢复备份与独立审计历史导出，或版本化的分块格式。旧壳缓存清理必须与 R4 的活跃版本保护一起实现。

验收：长期修订积累、接近配额、导出超限、归档后恢复、旧客户端在线等场景；清理失败不破坏主账本。

**R9 · P2 · 服务端隐藏错误响应的同时也丢弃了内部诊断证据**

位置：`server/app.ts:87,108–132`；`server/backup.ts` 的定时任务异常处理。

Fastify logger 被关闭，500 错误统一转换为通用响应，没有保留内部错误类型、堆栈、请求标识或 SQLite 错误码。备份界面有一般失败提示，但不同根因容易归为同一种错误。磁盘满、只读卷、SQL 错误、程序错误将难以区分；健康探针 SELECT 1 也不能证明写入路径正常。

方案：保持对外响应不泄漏细节，内部启用脱敏结构化日志，记录 request ID、路由模板、耗时、错误类别/码以及必要堆栈；不记录 Cookie、CSRF、密码、请求正文、账本内容。区分存储错误与业务拒绝，并增加备份失败和空间不足的运维信号。写入探测应独立于普通健康检查并审慎设计。

验收：模拟磁盘/权限失败及意外异常，能关联请求与原因，同时确认日志没有凭据或财务数据。

**安全性评价**

代码已有 scrypt 密码派生、随机会话令牌及哈希保存、HttpOnly/SameSite/Secure Cookie、Origin 与 CSRF 双校验、登录限流、参数化 SQL、CSP、容器非 root/只读文件系统、SQLite 备份完整性校验。相关自动化用例通过。这些应保留，不建议为性能优化绕过校验。

本次未发现足以确认的直接认证绕过、SQL 注入或脚本注入链。外部依赖审计也未报告已知漏洞，但这不是完整渗透测试结论。仓库 Compose 默认自动备份关闭且备份在数据卷内，应按既有产品决定处理；本次没有启用自动备份。独立介质备份、还原演练和设备存储压力验证属于运行保障，不能由 API 测试替代，也未核实当前 NAS 是否另有这些措施。

**可维护性评价与后续调整**

- 领域模块已拆分，TypeScript 开启 strict，金额使用 BigInt；这些方向合理。主要缺口是“界面规则、旧快照操作、本机保存、服务端协议”之间未形成唯一可执行规则，R1/R5 是具体后果。
- `Reports.tsx` 1273 行、`ServicePanel.tsx` 1111 行、`EntryForm.tsx` 1082 行、`engine.ts` 889 行。建议按表单命令、数据访问、同步阶段、展示组件拆分，在增加边界测试之后逐步做；单纯拆文件不能修复一致性。
- `docs/product-design.md:439,468` 和 `docs/technical-design.md:45` 仍写“不采用市场报价／外部汇率移出 MVP”，但 `docs/implementation-plan.md:161` 已明确纳入 Frankfurter；现有 `reporting.ts:169–175` 还区分收入、消费与转账推导汇率优先级。应编写当前生效的计价规则与优先级决策记录，把旧规则标注为历史，避免下一次修改按过时文档回退。此项是文档与规则来源不一致，不在本轮擅自认定所有支出都必须改按市场价。
- 仓库未发现 `.github` CI 配置；已有良好本地脚本，但需要在所使用的 CI 中强制 check、全量测试和隔离构建。不能据此认定外部 CI 一定不存在。
- 给上述竞争条件加入正式回归测试，并补少量真正浏览器的关键流程验证，尤其多页面保存、升级期间未保存表单、离线报表资源。现有纯模型/VM 用例不能覆盖 Safari 调度与页面生命周期。

**建议实施顺序**

1. 先修 R1/R2/R3，补回归测试，再验证原有同步幂等、冲突处理、恢复、升级用例。三项都涉及用户数据或输入保全，不宜与大型重构混在一起。
2. 随后修 R4/R5/R6/R9：旧缓存资源路由、币种规则统一、报价缓存时间模型和脱敏诊断。每项可以独立、小范围提交。
3. 用基准数据推动 R7/R8：先消除空轮询的整本读取，再减少重复全账计算；容量治理与安全归档一起设计。最后做目标 iPhone 的离线、升级、长任务和存储压力验证。
4. 同步更新现行领域规则文档，接入 CI，再渐进拆分大型模块。任何涉及 IndexedDB/同步协议变更的优化，都要带迁移、旧版客户端兼容和回退验证。

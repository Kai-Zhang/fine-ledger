# 厘序首版技术设计

版本：0.2
日期：2026-10-27
依据：[首版需求 0.4](requirements.md)
状态：正式架构待分阶段验收；P0 已开始独立产品原型，范围和验证记录见 [P0 评审说明](p0-review.md)。

产品名为“厘序”，项目 codename 为 `fine-ledger`。采用本地优先 PWA、家庭 NAS 单实例服务和显式增量同步。手机上的新增与查询不等待服务器；NAS 保存各设备共同认可的版本，并负责完整性校验、冲突检测和恢复。

本文件给出模块、存储、同步协议、金额计算、部署和验证边界，不包含实现代码或数据库建表脚本。实施顺序见[分阶段实施计划](implementation-plan.md)。

## P0 产品原型与正式架构的边界

旧技术 demo 已整体归档到 `archive/technical-demo-2026-10-27/`，保留技术验证证据；新界面从零实现，独立端口 4180、IndexedDB `fine-ledger-p0-review-v1`、Service Worker 缓存前缀 `fine-ledger-p0-shell-`，不读取旧运行数据，也不连接旧 NAS 接口。

P0 为方便快速评审采用无第三方依赖的浏览器 ES modules、CSS 和 Node 静态服务；它是临时交互实现，**没有完成**下表计划中的 TypeScript / React / Vite / Dexie / Fastify 工程化选型。P1 启动前应按最终确认的交互拆分页面组件与领域模块，落实正式 schema，不把原型的整体 book 存储或 outbox 意图直接当作 P2 同步协议。

本原型的金额使用 BigInt 运算及最小单位整数字符串。业务记录、创建操作意图及对应草稿清除在一个 IndexedDB readwrite 事务中完成，先读取该事务的最新账本再验证剩余退款和账户余额，避免两个标签页基于旧内存写入丢失。保存成功只在 transaction complete 后反馈；失败保留表单。调整金额在事务内由最新余额与目标余额求差。导出在单个 readonly 事务中读取账本、草稿与全部操作意图。

描述候选先按描述规范化去重（同一类型的最新记录），再作 substring 筛选与 prefix 优先稳定排序，默认最多 8 项。此处只适用于小型合成账本；正式万级账本应维护描述历史索引，不在每次输入时全量排序。P0 时间输入分钟精度，保存显式补秒为 00 并转 UTC；正式历史迁移不能把原有非零秒截断。

Service Worker 预缓存本地应用壳，不缓存 API、不发远端字体或分析请求；不使用自动 skipWaiting，避免录入中途强制接管。P0 代码发布更新需关闭该来源全部页面后重新打开，见评审说明。NAS、完整认证、迁移、冲突与恢复逻辑尚未接入。

## 架构与技术选择

| 层次 | 选择 | 目的 |
| --- | --- | --- |
| 手机及桌面界面 | TypeScript、React、Vite，响应式布局 | 共享界面组件，手机记账和桌面对账采用不同布局 |
| 本地持久化 | IndexedDB，使用 Dexie 管理事务和索引 | 保存业务副本、操作队列、草稿及同步游标 |
| 离线应用资源 | Service Worker、Workbox 预缓存 | 离线启动；不承担后台定时同步 |
| 业务规则 | 独立 TypeScript 领域模块 | 前端离线校验与后端入库校验使用同一套金额和业务规则 |
| NAS API | Node.js 受支持的 LTS 版本、Fastify | 提供认证、同步、快照和迁移接口 |
| NAS 数据库 | SQLite，本地持久卷，单服务实例 | 事务、关系约束、版本日志和便于恢复的备份 |
| 报表 | 客户端查询和汇总；重计算放入 Web Worker | 离线可用，复杂汇总不阻塞输入 |
| 验证 | Vitest、Playwright、真实 iPhone 和 NAS | 分别验证规则、浏览器流程和实际设备行为 |
| 部署 | NAS 原有反向代理加应用容器；无容器环境再适配常驻服务 | 同源 HTTPS、稳定地址、持久化和定时备份 |

React 和 Vite 分别提供界面组件模型与前端构建能力；Fastify 用于 API。具体版本、SQLite 驱动及容器 CPU 架构在实施第零阶段锁定，不在未检查 NAS 前指定镜像标签。[React 文档](https://react.dev/learn)、[Vite 文档](https://vite.dev/guide/)、[Fastify 文档](https://fastify.dev/docs/latest/)

不引入微服务、Redis、消息队列、外部托管同步平台或实时 WebSocket。当前万级交易规模允许保存完整本地业务副本；NAS 即使暂时关闭也不阻止已初始化设备记账。也不采用直接同步整个 SQLite 文件的方式，多设备合并以业务操作为单位。

## 存储模型与事务边界

业务实体以[需求文档的数据模型](requirements.md)为准，技术存储增加同步基线、工作副本和约束版本。账本、账户、分类、项目、交易、流水、退款、对账、成本来源、还款覆盖和迁移归档均有稳定 ID。

### 本地数据库

| 存储组 | 内容 | 是否可重建 |
| --- | --- | --- |
| server_base | NAS 已确认的业务实体与版本 | 可从 NAS 重建 |
| working_data | 基线叠加本地待提交操作后的可见实体 | 可由基线及完整操作队列重建 |
| outbox | 操作意图、依赖、首次提交后冻结的请求体和响应状态 | 不可丢弃，可能是离线记录的唯一来源 |
| conflicts | 基础、本地、远端版本及关联待提交操作 | 解决前保留 |
| drafts | 尚未保存为交易的输入 | 本机独有，不能以同步成功代替草稿保存 |
| sync_meta | 设备、账本、服务端代次、拉取游标、协议版本 | 与相应数据一同更新 |
| report_cache | 汇总与索引缓存 | 可重建，不是账务来源 |

首次实现可按业务表分别维护基线与工作视图，无需设计通用对象数据库。一个 Dexie 事务同时提交工作副本变更和 outbox 意图；事务中不等待网络。Dexie 的事务 Promise 在提交后才成功返回，异步网络等待可能使 IndexedDB 事务提前失活，因此同步必须放在事务之外。[Dexie 事务文档](https://dexie.org/docs/Dexie/Dexie.transaction())

默认按账户与记账日期、业务日期、分类、项目、入账状态建立索引；描述搜索在当前数据规模先做规范化文本匹配。批量迁移或重建报表使用分块任务，不能在每次按键后扫描全账本。

### NAS 数据库

采用关系表存储业务实体，外键、唯一约束和应用级校验共同保护一致性。迁移原始记录和修订负载允许用版本化 JSON 或二进制归档字段，不让核心关系只藏在 JSON 中。

额外系统表包含：操作回执、变更批次、修订历史、设备与会话、账户活动版本、还款分配版本、快照清单。操作回执唯一键为账本 ID 与 operation_id，并保存请求摘要；同 ID 不同内容直接拒绝。

SQLite 采用 WAL、开启外键、有限 busy timeout，并以同步持久化优先的配置提交账务。服务端只有一个写入进程，事务保持短小。SQLite WAL 不支持跨主机网络文件系统，因此数据库位于 NAS 上服务进程可直接访问的本地文件系统或容器本地挂载卷，不放在另一台机器的 SMB/NFS 挂载路径，也不让客户端打开数据库文件。[SQLite WAL 文档](https://sqlite.org/wal.html)

### 业务聚合与跨实体一致性

| 操作 | 同时受保护的数据 |
| --- | --- |
| 保存／修改交易 | 交易、账户流水、分类拆分、相关项目关联 |
| 保存转账 | 同一交易的转出与转入两端，以及独立费用的关联 |
| 确认银行入账 | 原交易、正式账户金额、入账状态、中间金额历史、成本分配 |
| 关联退款 | 退款、原支出可退量、成本冲减及未偿本金影响 |
| 分配外币还款 | 还款批次、已偿本金覆盖、成本来源余额、消费成本分配 |
| 完成对账 | 对账批次、确认的流水版本、账户活动版本 |

每个命令声明读到的相关实体版本。只检查还款交易自身版本不足以防止两个设备同时消费同一成本来源，因此还要检查成本来源版本、目标本金版本和账户还款分配版本。

账户活动版本在影响已入账余额的新增、修改、删除时递增，用来防止“对账期间另一设备新增了一笔流水”的遗漏。账户还款分配版本在消费本金、退款、还款和区间边界变化时递增。字段与版本均由服务端更新，不信任客户端报告“校验通过”。

## 金额与状态规则

### 精确金额

- 原币及账户金额以最小货币单位整数表达；CNY/USD 使用分，JPY 使用元。
- 领域模块使用 BigInt 做整数和比例分配；跨 JSON 与本地持久化边界使用规范化十进制整数字符串。SQLite 驱动必须无损读写 64 位整数，溢出边界拒绝输入，不静默降为浮点数。
- 汇率采用十进制字符串及明确精度，运算时转为整数分子／分母；禁止 Number 浮点累计账务。
- 分配采用最大余数法：先取各项整数分，再按余数和稳定目标 ID 分配尾差。退款等负向值先按绝对值分配再恢复方向。
- 部分分配把未分配本金作为额外一项同时分配来源总 CNY 成本，或按剩余本金／剩余成本继续分配，保证累计不漂移。
- 输入超过币种精度时提示修正；历史浮点导入的舍入另列核验差异，不自动写成余额调整。

### 日期与状态

业务日期与银行记账日期用明确的日历日期，时间戳单独用 UTC；账本业务时区决定默认“今天”，不会因旅行跨时区重写已有日期。排序用日期、可用业务时间和稳定 ID，不用同步到达时间冒充银行顺序。

| 维度 | 示例状态 | 影响 |
| --- | --- | --- |
| 入账 | pending、posted、voided | 是否进入账户正式余额和对账 |
| 本地提交 | saved、queued、sending、conflict、rejected、synced | 数据保存和跨设备可见性 |
| 对账 | 未核对、历史已核对、属于有效完成批次 | 是否已与外部记录核对 |
| 实际成本覆盖 | none、partial、full | 还有多少本金缺少实际 CNY 成本 |
| 成本质量 | confirmed、estimated、legacy_estimated、unpriced | 报表确定程度 |

pending 的正式账户金额可空，中间 USD 数值只保存在 BankAmountObservation。确认入账更新同一交易和流水身份，报表用新成本替换旧暂估，既不新增消费，也不让中间 USD 进入 CNY 余额。

退款涉及两个投影：账户流水记录实际到账；报表冲减原消费相应历史成本，差异进入单列的汇兑结果。退款成本与原消费拆分保持可追溯。待入账撤销只撤销暂估，不虚构退款流水。

## 还款分配设计

### 默认区间与覆盖

每笔转入外币信用卡、明确标为还款的有效 posted 转账触发 RepaymentBatch。普通退款和余额调整不推进“上次还款”边界；人民币信用卡还款不参与这套外币成本重新计算。

规则版本首版定为 `repayment-window-v1`，步骤如下：

1. 获取同一外币信用卡账户的上次有效还款与本次还款，冻结 `(previous_date, current_date]`。首次还款读取迁移确认的起始日及期初欠款项。
2. 收集区间内 posted 消费及明确的费用负债，扣除已关联退款和此前有效 RepaymentCoverage。加入区间前仍未偿的本金，优先处理这些结转项。
3. 按入账日期、可用入账时间、稳定流水 ID 逐笔覆盖本金，允许覆盖一笔的一部分。待入账、已撤销和删除项不参与。
4. 保存已偿本金到 RepaymentCoverage，再依据已知 CostSource 计算 CNY 成本并落入 CostAllocation。来源未知时覆盖记录仍有效，CNY 成本待核定，之后不能用另一笔还款再覆盖一次。
5. 金额不够时保留未偿部分；超额时保留未分配本金及 CNY 成本，不把更多成本强塞给已全额覆盖的消费。
6. 同日多次还款采用稳定顺序，后一次只处理尚未覆盖量。晚补的同日或旧日交易标记为待补分配，不重新洗牌历史结果。
7. 保存候选输入的版本摘要、边界、来源、算法版本和结果。服务端按相同规则重算与校验，输入变化则返回冲突；不能静默给出与本机不同的“成功分配”。

“上期结转先于本期”是处理部分还款的技术补充。未知期初欠款无法确定时，保留真实还款及未分配金额并提示，不自动假设所有历史消费都未偿。

### 保存真实还款与保存分配分别处理

转账资金流水是一个原子命令，随后自动产生依赖该命令的分配命令。这样分配发生冲突不会丢掉真实还款；界面应显示“还款已记录，分配待处理”，不能显示全部完成。分配命令内部的批次、覆盖与成本行仍必须整体成功或失败。

手动调整为低优先级：后续通过替代版本修正批次，不直接覆盖旧行；必须同时释放旧覆盖、回收旧成本分配、生成新分配并验证受影响后续批次。早期没有调整 UI 时，复杂例外可保留待处理，禁止绕过约束改库。

### 先换汇及其他边界

银行购汇还款同一步完成时，只需要 CNY → 外币信用卡这一笔转账。先换汇再还款时，通过 CostSourceLink 将选定外币资金的 CNY 成本传给还款来源；每次传递扣减上游可用量，不创建第二份可花费成本。首版按用户选择来源操作，不实现自动全链路资金溯源。

原币、入账币和还款币不同时，先按信用卡入账币覆盖债务，再按原币拆分比例分配 CNY。退款冲减采用稳定关联，修改已使用成本的退款或本金时，相关批次转待核验。人民币成本已经确定并不等于信用卡已还款。

### 合成验收样例

| 输入 | 预期 |
| --- | --- |
| 上次 9 月 10 日、本次 10 月 10 日；9 月 9 日消费、9 月 12 日入账 | 进入本次区间；按入账日而非消费日判断 |
| 本期 40 USD 和 60 USD，偿还 100 USD 花费 720 CNY | 两笔成本 288、432 CNY；还款不算支出 |
| 上期剩余 20 USD，本期新增 80 USD，本次偿还 50 USD | 先覆盖旧 20，再覆盖新 30；余下 50 结转 |
| 一笔 100 USD，先以 288 CNY 偿还 40，再以 444 CNY 偿还 60 | 最终成本 732 CNY，第一次确认的 288 不被重估 |
| 欠款 80 USD，偿还 100 USD 花费 720 CNY | 消费分配 576 CNY；20 USD 与 144 CNY 留在未分配余额 |
| 外币还款 50 USD，原换汇成本未知 | 覆盖 50 USD 债务，成本未知；下一次不得再次覆盖该本金 |
| 原币 10,000 JPY、中间 67 USD、暂估 482.40 CNY，最终入账 490 CNY | 同一笔消费成本变 490，保留历史数值，不进入外币还款分配 |

## 同步协议

### 同步时机与状态机

启动、恢复前台、保存后和前台有待同步任务时尝试。同一来源选出一个前台协调器；多标签可用数据库租约协调，租约失效允许接管。即使出现双发，服务端幂等仍是最终保障。PWA 与 Safari 不假设共用本地库，首次建立新存储环境按新设备初始化。

连接 NAS 超时后使用带抖动的指数退避，建议从数秒到上限约一分钟，停止可见页面之外的轮询。401 进入需重新认证；冲突和业务错误不无限重试；网络不可达保持本机可用。online 事件只作为提示，实际 API 请求决定可达性。

### 传输接口草案

| 接口 | 用途与关键数据 |
| --- | --- |
| GET /api/v1/meta | 协议与最低支持版本、服务器代次；不泄露账本内容 |
| POST /api/v1/session | 登录并建立设备会话 |
| DELETE /api/v1/session | 撤销当前会话，不自动清空本机未同步记录 |
| GET /api/v1/snapshot | 鉴权后获取固定水位的完整业务快照及校验清单 |
| POST /api/v1/sync/push | 有依赖顺序的命令列表；返回每条命令的提交、冲突或拒绝结果 |
| GET /api/v1/sync/pull | 从游标获取完整提交批次，返回 next_cursor、has_more 和服务端水位 |

每条上传命令包含协议版本、账本与设备 ID、server_epoch、operation_id、类型、预期实体版本／账户版本、依赖操作、数据负载与摘要。operation_id 由客户端生成，创建时间只用于审计，不用于覆盖决策。

### 本地连续修改

同一交易离线连续编辑时，outbox 保存有序意图和依赖链。未尝试发送的后续意图可在前序命令确认后，使用其返回版本形成请求；若其依赖基线已被其他设备改动，进入冲突，不能自动换成最新版本强推。首次发送的请求冻结 ID、内容和版本，超时只重发相同内容。

前序冲突或拒绝时，阻止依赖它的后续操作，但允许不相关交易同步。工作视图保留用户内容并标识冲突，不把未获服务端接受的数据装成已同步数据。

### 服务端提交

每条业务命令执行以下单个 SQLite 事务：检查 epoch 和权限、按 operation_id 查询旧回执、核对请求摘要、检查全部预期版本、执行业务校验、写业务变化与修订、追加提交批次、写回执，最后提交。只有提交完成才返回成功。

同一操作重试返回原回执。批量请求允许逐命令成功或失败，但一条命令的所有业务行不可拆开；依赖失败的后续命令不执行。回执含修订及对应提交序号，不能让客户端把“某次上传成功的序号”直接当作已拉取游标，跳过中间其他设备的变化。

### 拉取与合并

变更按服务端单调提交序号排序，分页只在完整提交批次边界切分。客户端在一个 IndexedDB 事务中更新 server_base、匹配已确认 outbox、重建受影响 working_data，并推进 pull_cursor；中断后重复拉取安全。

保留本地待提交覆盖层。远端版本与本地编辑基础相冲突时，保存三方版本并提示解决。金额、账户、退款、入账、成本和对账都不采用最后写入者获胜；首版以整笔业务为冲突单位，不追求逐字段自动合并。

报表每个业务对象只取工作视图中的一个版本，不同时累计基线和覆盖层。若筛选范围包含冲突对象，报表标识“含本地冲突版本”；正式完成对账仍要求相关冲突已解决。

冲突解决产生新的操作 ID。不能只给旧失败请求换一个 base_revision 再提交，从而隐藏用户没有看过的远端修改。

### 快照、删除和恢复代次

快照以固定 commit_cursor 读取，分块数据均属于同一水位；客户端校验完成后原子切换基线，再从该水位拉取。初版保留操作回执、删除墓碑和必要变更历史，不为小账本过早做清理。

未来压缩日志导致游标过期时，先保留并导出 outbox 与冲突记录，再获取快照、重新校验待提交操作，禁止清库重来。

服务端从旧备份恢复时生成新的 server_epoch。旧客户端停止自动上传，不直接把旧基线覆盖回恢复后的服务器；通过恢复流程比较本地副本、备份水位后的交易和未同步操作，再确认需要补回的数据。已被旧服务器确认但晚于备份的数据也可能只存在客户端，不能只检查 outbox。

## 离线资源与发布

静态界面、核心脚本、图标和必要字体均由同源提供并预缓存；记账页面不能依赖 CDN 字体或外部脚本。首次初始化完成后做资源与数据库就绪检查，界面明确显示可离线使用。Workbox 提供安装阶段的资源预缓存，但仍需验证实际离线入口和完整资源清单。[Workbox 文档](https://developer.chrome.com/docs/workbox/modules/workbox-precaching)

API 请求不靠 HTTP 缓存充当账本，业务响应不写入通用资源缓存。数据库由本地存储层管理，退出登录时不自动删库；清除设备数据需先处理未同步内容。

新 Service Worker 完整安装后进入等待，不在用户输入中强制刷新。更新前保存草稿、检查数据库兼容性，用户在空闲时应用。前端构建版本、本地 schema、同步协议和服务端 schema 分别版本化；首版服务端尽量兼容当前与上一客户端协议，无法兼容则停同步但保留本地读取、导出和旧版允许的记账。

数据库升级采用可中断恢复的迁移记录。破坏性迁移前导出本地业务及 outbox，并生成 NAS 一致性备份。服务端镜像回退并不代表数据库可以直接降级，回退流程必须说明使用兼容 schema 还是恢复备份。

申请持久存储并显示申请结果，检测配额错误和低空间。WebKit 默认存储是 best-effort，persist 请求受浏览器策略判断，因此不把申请成功与永久不丢失画等号。离线未同步数据仍有设备丢失或数据清除风险，界面展示待同步数量和最长等待时间。[WebKit 存储政策](https://webkit.org/blog/14403/updates-to-storage-policy/)

## NAS 部署、认证与备份

### 网络和运行环境

采用固定 HTTPS 域名、家庭 DNS 指向 NAS、同源静态资源与 API。域名的 DNS-01 证书验证可以不开放 NAS 的公网入站端口；NAS 只需具备完成续期所需的出站访问。证书自动续期与到期提示纳入部署验收。[Let’s Encrypt 文档](https://letsencrypt.org/docs/challenge-types/)

容器只开放反向代理需要的内部端口，数据库目录和归档目录使用持久卷。应用构建在开发机或构建环境完成，NAS 运行发布产物。必须先确认 NAS 型号、CPU 架构、容器能力、本地卷及家庭 DNS；这些是部署输入，不是当前已验证的条件。

### 认证与数据保护

首版单用户密码登录，服务端使用带独立盐的 scrypt 派生密码校验值，参数在目标 NAS 上校准；会话使用随机高熵标识和 HttpOnly、Secure、SameSite Cookie，服务端支持设备撤销。Node.js 提供 scrypt 等密码学 API；不自制哈希或加密算法。[Node.js crypto 文档](https://nodejs.org/api/crypto.html)

所有读写账本 API 做鉴权与账本授权；变更请求验证 Origin 和 CSRF 保护，限制登录尝试和请求体大小。局域网可达不等于已授权。设备 ID 只是标识，不是凭证。

前端采用内容安全策略、输出转义，不引入第三方分析脚本。服务端日志不记录交易描述、金额、完整负载、Cookie 或凭证。密码忘记通过 NAS 管理入口重置并撤销会话，不发送外部邮件。

首版信任 NAS，不提供端到端加密或以界面锁代替数据库加密的承诺。NAS 磁盘与备份按环境加密，备份恢复密钥单独保存；远程撤销会话不能擦除一台离线设备已有的数据。

### 备份和恢复

使用 SQLite Online Backup API 或等价的一致性快照机制，不能定时只复制正在写入的主数据库文件。完成快照后校验，再复制到独立故障介质。SQLite 官方备份 API 支持在线生成一致性数据库副本。[SQLite 备份文档](https://sqlite.org/backup.html)

建议默认每日快照，保留最近 14 个日版本、8 个周版本、12 个月版本；升级和大批导入前额外备份。该保留策略可配置，不能把未设置的独立备份目标标为已保护。

备份清单包含 schema、协议、构建版本、账本 ID、快照水位、时间、文件校验值及归档文件清单。会话凭证不作为恢复后继续有效的身份，恢复时撤销并重新登录。

恢复步骤是停止写入、保存当前故障副本、校验目标备份、恢复数据和归档、改变 server_epoch、重启、核对余额与关键关联、逐设备处理恢复分歧。目标数据损失窗口为最近一次成功备份之后的已同步记录，以及尚未上传的本机记录；不能承诺零丢失。恢复时间在演练后测定。

## MoneyWiz 迁移

迁移是独立工具流程，默认不让应用服务扫描私人目录。读取用户明确提供的副本，包含 SQLite/WAL 组合，通过 SQLite 生成一致性快照，记录输入指纹，不修改原文件。

步骤依次为：实体与用户域识别、源记录标准化、旧 ID 映射、转账配对、退款与分类关联、币种和金额转换、标签项目映射预览、预算归档、独立目标库试导入、关系与余额核验、确认正式导入。

源表的重复别名列不能凭命名覆盖；映射规则用样例和引用完整性验证。原始来源 ID、源类型和转换规则版本保留在 LegacyMapping。迁移 ID 由导入批次与源身份确定，重复执行不重复创建记录；不同备份间的增量合并不是首版承诺。

不能证明的历史汇率关系保留为历史暂估，不能仅依据新增默认还款区间规则就宣称历史成本准确。业务原始预算内容完整归档，旧认证字段从新业务库排除。原始备份仍单独保存。

全量导入以一致快照交付给设备，不要求移动端上传上万条普通 outbox 操作。正式迁移冻结账本写入，在导入事务或隔离目标库中完成，再切换账本代次；已有离线记录必须先归档和合并，不能被新快照覆盖。

正式替换导入使用新的 ledger_id，原账本只读归档；客户端发现当前账本已被替换时停止向旧账本自动提交。server_epoch 专门用于服务器备份恢复，两种变化都要求保留本机内容后再进行受控恢复或迁移。

## 测试、可观测性和设计风险

规则测试覆盖金额守恒、退款上限、成本来源不超用、分次还款、区间边界、状态转换和历史修订。同步集成测试注入响应丢失、请求重复、写入失败、乱序、跨设备并发、快照中断和服务端恢复。

浏览器流程使用 Vitest 与 Playwright；Playwright WebKit 不能替代真实 iPhone 主屏幕 PWA 验收。真机验证离线冷启动、锁屏切换、保存后强退、软键盘、低存储失败、版本更新和家庭网络切换。[Vitest 文档](https://vitest.dev/guide/)、[Playwright 浏览器文档](https://playwright.dev/docs/browsers)

记录本地保存耗时、启动耗时、队列长度与最老操作时间、同步时延、冲突数、API 错误、备份成功时间和快照大小。默认只在本机或 NAS 查看，不外发统计。报告数据版本、来源构建和运行设备必须一起记录。

| 风险 | 处理与实施门槛 |
| --- | --- |
| iOS 离线资源或本地存储行为不满足要求 | 第零阶段先真机验证；未通过不扩大功能开发 |
| 待入账与正式金额双计 | 稳定交易 ID、状态约束与成对验收样例 |
| 多设备同时分配同一来源 | 跨实体版本校验和服务端单事务 |
| 日期区间无法重建真实历史还款关系 | 只作新增默认规则，历史关系单独验证或标暂估 |
| NAS 断电、磁盘满、数据库恢复 | 提交后确认、一致性备份、恢复代次与故障注入 |
| 长期离线客户端或软件升级 | 版本握手、保留队列、可恢复迁移与快照重建 |
| 过多资金溯源功能拖慢首版 | 先支持两种已确认信用卡路径和手动成本来源，自动溯源后置 |

这些是需要验证的设计措施，不表示实现已经具备相应可靠性。阶段通过标准以[实施计划](implementation-plan.md)为准。

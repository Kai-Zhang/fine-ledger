# 0.3.1 固定入口更新修复

日期：2026-10-27。用户反馈 Safari 和主屏幕应用仍看到旧界面；要求端口与访问方式保持不变。

## 当前入口

**<https://zhangkaidemac-mini.local:8445/>**

原本使用 IP 的设备继续使用 **<https://192.168.0.241:8445/>**。入口不附参数，不要求清除网站数据或删除/重装图标。8445 端口、域名、证书、本机库名与已有账目保持不变。

## 问题与修复

旧 worker 使用 cache-first 导航，并让新 worker 等待；旧页面没有操作新 worker 的更新按钮，所以旧缓存可能一直控制入口。之前给页面加版本参数只提供了旁路，没有闭合旧 worker 自动切换；直接取服务器新文件也不能证明旧客户端已经更新。

0.3.1 改为：

1. 根 HTML、worker 与发布描述使用 `Cache-Control: no-store`。在线导航获取服务器当前入口。
2. JS、CSS、领域模块及离线 HTML 构建到 `/assets/<版本-内容指纹>/`。资源没有查询参数，旧缓存无法用同名旧代码替代新发布；这些不可变资源可长期缓存。
3. 新 worker 完整预缓存成功才调用 skipWaiting 和 clients.claim。旧页面不支持消息握手时，从相同地址自动导航到新入口，不等待旧页面里不存在的更新按钮。
4. 新页面回复 build 与是否正在录入。正在录入不强制重载；退出表单后等待草稿事务完成，再回到原根地址应用更新。
5. 离线入口由同一内容版本的 HTML 固定写入缓存；请求失败时使用该发布，保留离线启动。整个过程不删除 IndexedDB、草稿或操作队列。

构建入口为 `npm run build`；HTTP/HTTPS 服务启动自动构建。运行中修改源码后运行构建即可发布到相同地址。内容未改变时构建指纹不变。构建先写完整资源，再以原子文件替换入口、worker 和发布描述；旧资源目录保留，以供打开中的旧客户端引用。

## 实际回归

- 自动化 **21/21** 通过，其中 5 项针对 worker 安装失败不接管、旧页面同址迁移、正在录入时延后、网络优先/离线固定发布，以及构建确定性和无参数资源地址。
- 真实桌面浏览器的隔离 scope 中先安装 cache-first 旧 worker，页面确认“旧版缓存页面”；保存一笔合成测试交易与草稿。部署新 worker 后只刷新相同 URL，页面自动切换“新版页面”，地址未变，交易与草稿标记保留。临时测试文件已移除，未操作真实账本。
- 实际应用在无参数 `http://localhost:4180/` 打开。保持金额 12.34、描述“更新保护草稿”的表单，再发布另一个内容版本：旧表单未被刷新；关闭后自动加载新指纹版本，再打开时金额和描述仍在。
- 停止本机 4180 服务（确认无监听）后，从相同根地址重载，仍加载新的固定发布，草稿完整。8445 服务始终可用；随后 4180 已恢复。
- 原 8445 HTTPS 根地址、IP 地址严格使用原 CA 验证；根入口、10 个发布资源、worker 和发布描述均与部署文件一致。缓存头和指纹见 [验证结果](review/v0.3.1-update-verification.json)。

以上为真实桌面浏览器生命周期回归和 Mac 端 HTTPS 核验，没有代替用户检查 iPhone 当前缓存容器。用户在原页面普通刷新即可触发旧缓存迁移；迁移可能先短暂显示旧缓存，再自动刷新为新界面。

依据：[Service Worker 生命周期](https://web.dev/articles/service-worker-lifecycle)、[skipWaiting](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/skipWaiting)。这里测试了缓存中的旧客户端，不能用 DevTools 的“Update on reload”替代用户路径。
